01. 제품 프로세스를 세분화하는 방법

[이 장의 핵심] 코드를 작성하기 전에 먼저 "사용자가 보게 될 페이지, 각 단계에서 수행되는 작업, 백엔드가 필요한 단계"를 명확하게 분류하세요.

코드 작성을 시작하기 전에 한 가지 질문에만 대답하면 됩니다.

사용자는 사이트 접속부터 결제, 잠금 해제까지 어떤 화면을 거치게 되나요#

이 장에서는 아키텍처 다이어그램에 대해 설명하지 않지만 먼저 제품을 Codex가 이해할 수 있는 작은 작업으로 나눕니다.

💡 왜 이러는 걸까요#
Codex는 명확한 작업 경계를 요구합니다. 제품 프로세스는 로드맵과 같습니다. 먼저 사용자가 어디에 들어왔는지, 어디에서 질문에 답변하는지, 어디서 지불하는지, 어디에서 보고서를 읽는지 파악하여 나중에 코드를 작성할 때 여기저기서 보충하지 않아도 됩니다.

먼저 가장 짧은 사용자 경로를 그립니다.

[이 섹션의 핵심] 먼저 홈페이지에서 전체 보고서까지 사용자를 위한 최단 경로를 작성합니다.

유료 퀴즈 사이트로 가는 최단 경로는 다음과 같습니다:

홈페이지
  -> 답변 페이지
  -> 무료 소개 보고서
  -> 결제 페이지
  -> 전체 보고서
  -> 보고서를 저장하거나 다시 엽니다.

아직 로그인할 필요는 없습니다. 저렴한 일회성 보고서에서 가장 중요한 것은 마찰을 줄이는 것입니다.

💡 왜 이러는 걸까요#
로그인, 회원가입, 백엔드, 할인코드 모두 추후 추가 가능합니다. 첫 번째 버전에서는 더 많은 선반을 장식하기 전에 카운터가 실제로 돈을 모을 수 있는지 확인하는 것처럼 사용자가 전체 구매를 완료할 수 있습니다.

각 페이지에서 수행할 작업

[이 섹션의 핵심] 첫 번째 버전이 너무 무거워지는 것을 방지하기 위해 각 페이지는 하나의 주요 작업만 담당합니다.

홈

홈페이지는 사용자가 시작하도록 하는 역할만 담당합니다.

가지고 있어야 할 것:

  • 이 퀴즈가 사용자가 해결하는 데 도움이 되는 문제를 설명하는 한 문장입니다.
  • 시작 버튼.
  • 선택사항: 언어 전환, 케이스 입력.

처음에 "결제하여 잠금 해제" 또는 "지금 구매"라고 쓰지 마세요. 사용자가 아직 시간을 투자하지 않았으며, 너무 일찍 돈을 인출하면 완료율이 낮아집니다.

답변 페이지

답변 페이지는 사용자가 질문을 완료할 수 있도록 하는 역할만 담당합니다.

가지고 있어야 할 것:

  • 현재 문제 번호.
  • 질문.
  • 옵션.
  • 이전 질문/다음 질문입니다.
  • 진행 상황이 표시됩니다.
  • 그림이나 시각 자료.

초보자는 먼저 5문제의 테스트 버전을 수행한 다음 프로세스를 통과한 후 48문제로 확장하는 것이 좋습니다.

무료 소개 보고서

무료 버전은 기분전환용도 아니고 공허한 이야기도 아닙니다. 사용자가 당신이 전문가라고 생각하게 만듭니다.

다음을 표시할 수 있습니다.

  • 핵심 심리적 동인.
  • 행동 경향과 잠재적인 정체 지점.
  • 자기 인식과 외부 성과 사이의 격차.
  • 전체 보고서는 어떤 방향으로 계속 분석할 것인가.

표시하지 않음:

  • 직업 답변을 완료하세요.
  • 전체 경로.
  • 상세한 실행 계획.
  • 저장할 수 있는 전체 보고서.

페이월

페이월은 사용자가 지불하는 것만 허용합니다.

가지고 있어야 할 것:

  • 현재 가격.
  • 명확한 결제 버튼.
  • 결제 후 지침을 자동으로 잠금 해제합니다.
  • 결제 실패 또는 보류 상태입니다.

한 번에 너무 많은 결제 방법 버튼을 입력하지 마세요. 백엔드는 지역에 따라 입구를 추천할 수 있습니다.

전체 보고서

완전한 보고서는 사용자가 "이것은 임의의 텍스트 조각이 아니다"라는 느낌을 주어야 합니다.

포함할 수 있는 것:

  • 경력 레이더.
  • 심리적 프로파일링.
  • 적합한 직업 유형.
  • 다양한 개발 경로.
  • 위험 경계.
  • 대체 방향.
  • 보고서를 저장합니다.

보고서 ID란 무엇인가요?

【이 섹션의 핵심】reportId는 특정 테스트 보고서의 번호입니다.

reportId는 보고서의 번호입니다.

사용자가 질문에 대답한 후 프런트 엔드 또는 백 엔드는 reportId를 생성하고 모든 후속 작업은 이를 중심으로 진행됩니다.

이 답변 -> 보고서 ID
이 주문 -> 신고 ID
이번에 잠금 해제 -> ReportId
이 전체 보고서 -> 보고서 ID

reportId가 없으면 결제 플랫폼에서 "누군가 지불했습니다"라고 알려주며 어떤 보고서를 잠금 해제해야 할지 알 수 없습니다.

💡 왜 이러는 걸까요#
reportId는 픽업번호와 같습니다. 사용자가 식사를 주문하고, 결제를 한 후, 식사를 받으러 돌아올 때에도 동일한 번호를 사용하여 동일한 내용에 해당해야 합니다.

결제 세션이란 무엇인가요?

[이 섹션의 핵심] payment_session는 특정 결제 시도에 대한 기록입니다.

payment_session는 결제 시도입니다.

사용자는 다음을 수행할 수 있습니다.

  • 결제를 클릭하고 페이지를 닫습니다.
  • 결제에 실패했습니다.
  • 결제를 다시 시도하세요.
  • 결제가 성공적으로 이루어졌으나 프런트 엔드가 되돌아오지 않습니다.

따라서 프런트엔드 상태에만 의존하지 마십시오. 저장할 백엔드:```json

{

"sessionId": "pay_xxx",

"reportId": "rep_xxx",

"provider": "paddle",

"providerOrderId": "txn_xxx",

"status": "pending"

}


결제가 성공적으로 완료되면 다음으로 변경하세요.```json
{
  "status": "paid",
  "paidAt": "2026-05-28T00:00:00.000Z"
}
💡 왜 이러는 걸까요#
보고서에는 여러 번의 결제 시도가 있을 수 있습니다. 사용자는 처음에는 결제 페이지를 닫을 수 있지만 두 번째에는 성공합니다. payment_session는 상태 혼란을 피하기 위해 이러한 시도를 별도로 기록할 수 있습니다.

액세스 토큰이란 무엇인가요?

【이 섹션의 핵심】accessToken는 성공적인 결제 후 전체 보고서를 여는 열쇠입니다.

accessToken는 보고를 완료하는 데 핵심입니다.

결제가 성공한 후 백엔드는 추측할 수 없는 토큰을 보고서에 보냅니다. 다음에 사용자가 돌아올 때 프런트 엔드는 백엔드에 토큰을 묻습니다.

이 토큰에는 보고서 reportId를 볼 수 있는 권한이 있습니까#

전체 보고서는 백엔드에서 '예'라고 답한 후에만 표시됩니다.

💡 왜 이러는 걸까요#
전체 보고서를 표시하려면 "누군가 이 보고서 ID에 대해 비용을 지불했습니다"에만 의존해서는 안 됩니다. 그렇지 않으면 다른 사람이 동일한 보고서 ID를 볼 수 있습니다. accessToken는 전용열쇠와 같아서, 열쇠를 가진 사람만이 열 수 있습니다.

첫 번째 버전에서는 아무것도 할 수 없습니다

【이 섹션의 핵심】 첫 번째 버전은 잠금 해제를 위한 일회성 결제만 유지하며, 복잡한 기능을 수행하지 않으면 출시 속도가 느려집니다.

더 빨리 온라인에 접속하려면 첫 번째 버전을 건너뛸 수 있습니다.

  • 자동 이메일.
  • 여러 제품 패키지.

잠금을 해제하려면 먼저 일회성 결제를 한 후 천천히 추가해야 합니다.

💡 왜 이러는 걸까요#
제품 초기 단계에서 가장 확인해야 할 것은 "테스트를 완료하고 결제할 의향이 있는 사람이 있는가# "이다. 처음에 많은 주변 기능을 수행하는 것보다 먼저 이 메인 라인을 실행하는 것이 더 가치 있습니다.

**【이 단계의 핵심】 프로젝트가 아직 Git 웨어하우스가 아닌 경우 먼저 Git 웨어하우스로 만드세요. **

### 7단계: GitHub 원격 저장소에 연결

**[이 단계의 핵심] 로컬 Git에 이 프로젝트를 푸시해야 하는 GitHub 저장소를 알려줍니다. **

GitHub가 창고를 구축한 후 일반적으로 다음과 같은 주소를 제공합니다.

origin는 원격웨어 하우스의 로컬 Git 별명입니다. Git에게 다음과 같이 말합니다. 이제부터 원본으로 푸시한다는 것은 이 GitHub 저장소로 푸시한다는 뜻입니다.

> `git push`는 "로컬 아카이브를 클라우드 창고에 업로드"입니다. 그러면 Zeabur는 컴퓨터의 폴더 대신 GitHub의 코드를 읽습니다.

### 2단계: 백엔드가 하드 코딩된 포트가 아닌지 확인

const port = Number(process.env.PORT ##  8080);
const serverHost = process.env.PAYMENT_SERVER_HOST ##  "0.0.0.0";

});

3단계: 웹사이트 인증 제출

[이 단계의 핵심] 이전 장에서 얻은 Zeabur 도메인 이름을 Paddle에 입력하고 이것이 귀하의 판매 웹사이트인지 Paddle이 확인하도록 합니다.

Paddle의 웹사이트 승인 또는 도메인 확인 페이지에서 다음을 입력하세요.

https://your-zeabur-도메인 이름
https://도메인/가격
https://도메인/약관
https://도메인/개인정보
https://도메인/환불

이러한 URL은 직접 열 수 있어야 하며 웹사이트 홈페이지만 채울 수는 없습니다.

💡 왜 이러는 걸까요#
Paddle은 가격이 어디에 있는지, 규칙이 어디에 있는지, 개인 정보 보호 지침이 어디에 있는지, 환불 지침이 어디에 있는지 등 사용자의 관점에서 웹사이트를 살펴봐야 합니다. 전체 경로가 포함된 URL은 홈페이지보다 전달하기가 더 쉽습니다.

4단계: 기본 결제 링크 설정

[이 단계의 핵심] Tell Paddle: 나중에 결제를 생성할 때 결제 페이지에 어떤 확인된 도메인 이름을 사용해야 하는지.

기본 결제 링크를 작성하는 것이 좋습니다:

https://your-zeabur-domain/

여기서 흔히 저지르는 오해:

  1. 사용자에게 게시하려는 제품 링크가 아닙니다.
  2. 웹훅 URL이 아닙니다.
  3. 특정 ReportId에 대한 결과페이지가 아닙니다.
  4. Paddle이 결제 생성 시 사용하는 계정 수준의 결제 도메인 이름입니다.

기본 결제 링크가 설정되지 않은 경우 API 키가 정확하더라도 백엔드에서 거래 결제를 생성하지 못할 수 있습니다.

💡 왜 이러는 걸까요#
기본 결제 링크는 '결제 시스템에서 기본적으로 사용하는 매장 주소'라고 생각하시면 됩니다. 이 주소가 없으면 Paddle은 결제 페이지를 호스팅할 승인된 웹사이트를 알 수 없습니다.

5단계: 일회성 제품 만들기

💡 왜 이러는 걸까요#
제품은 "당신이 판매하는 것"입니다. 일회성 보고서의 경우 제품은 수업, 직업 서비스 또는 인적 컨설팅 약속이 아닌 디지털 콘텐츠에 대한 일회성 액세스여야 합니다.

### 7단계: API 키를 생성하고 Zeabur 변수에 넣습니다.

**【이 단계의 핵심】API 키는 백엔드에서만 사용되며 프런트엔드 공개 파일에 넣어서는 안 됩니다. **

Paddle 개발자 도구에서 API 키를 만듭니다.

그런 다음 Zeabur의 변수를 입력하고 다음을 입력합니다.```bash
PADDLE_ENVIRONMENT=sandbox
PADDLE_API_KEY=你的_sandbox_api_key
PADDLE_CNY_PRICE_ID=pri_xxx
PADDLE_USD_PRICE_ID=pri_xxx

참고:

  1. 샌드박스 키는 샌드박스 가격과 일치합니다.
  2. 라이브 키는 라이브 가격과 쌍을 이룹니다.
  3. 섞지 마세요.
  4. public/monetization.json에 API 키를 쓰지 마십시오.
  5. 프런트 엔드 .tsx, .js 및 .html에 API 키를 쓰지 마십시오.

올바른 개념은 다음과 같습니다.

브라우저 프런트 엔드: "결제하고 싶습니다"만 알 수 있습니다.
백엔드: 결제를 생성하려면 API 키를 Paddle로 가져가세요.
패들: 결제 페이지 URL로 돌아가기
💡 왜 이러는 걸까요#
API 키는 결제 백엔드 키와 같습니다. 사용자의 브라우저는 공개된 장소이므로 프런트 엔드에 있는 모든 항목이 표시될 수 있습니다. 키는 백엔드 또는 배포 플랫폼의 환경 변수에만 배치될 수 있습니다.

패들 알림 대상을 입력하세요.

https://your-zeabur-domain/api/webhooks/paddle

최소한 다음 이벤트를 선택하세요.

거래.완료
거래.결제_실패
거래.취소됨
transaction.past_due

그런 다음 웹훅 비밀을 복사하고 Zeabur 변수에 입력합니다.```bash

PADDLE_WEBHOOK_SECRET=你的_webhook_secret

PADDLE_ALLOW_UNSIGNED_WEBHOOKS=false


![패들 웹훅 신호](../../assets/diagrams/06-paddle-webhook.svg)

> 💡 **왜 이러는 걸까요#  **
> 웹훅은 Paddle이 적극적으로 백엔드에 "이 트랜잭션이 완료되었습니다."라고 호출하는 것과 같습니다. 웹훅 비밀은 양측이 합의한 비밀번호와 같습니다. 비밀번호가 없으면 누군가 가짜 전화를 걸어 돈을 지불했다고 말할 수도 있습니다.

### 9단계: 백엔드에서 Paddle 체크아웃을 생성하도록 허용

**[이 단계의 핵심] 사용자가 결제 버튼을 클릭하면 프런트엔드에서는 백엔드만 요청하고 Paddle API 키에는 직접 접속하지 않습니다. **

프런트엔드 요청:```http
POST /api/payments/checkout
Content-Type: application/json

{
  "reportId": "rep_xxx",
  "region": "domestic"
}

백엔드는 다음을 수행해야 합니다.

  1. 로컬 결제 세션을 생성하세요.
  2. 지역에 따라 PADDLE_CNY_PRICE_ID 또는 PADDLE_USD_PRICE_ID를 선택하세요.
  3. Paddle 생성 트랜잭션 API를 호출합니다.
  4. reportId를 custom_data에 넣습니다.
  5. payment_session_id를 custom_data에 넣습니다.
  6. Paddle 거래 ID를 저장하세요.
  7. Paddle 체크아웃 URL을 프런트 엔드로 반환합니다.

Codex에 대한 팁 단어:

이미 Zeabur HTTPS 도메인 이름이 있고 이제 Paddle에 연결하고 싶습니다.

새 패들 공급자를 추가하세요.

요구사항:
1. 테스트를 용이하게 하기 위해 모의 공급자를 유지하십시오.
2. POST /api/paids/checkout은 Paddle 생성 트랜잭션을 호출합니다.
3. 국내에서는 PADDLE_CNY_PRICE_ID, 해외에서는 PADDLE_USD_PRICE_ID를 사용하세요.
4. 거래 custom_data에는 reportId 및 Payment_session_id가 포함되어야 합니다.
5. 모든 비밀은 process.env에서만 읽을 수 있습니다.
6. public/monetization.json에는 비밀이 포함될 수 없습니다.
💡 왜 이러는 걸까요#
custom_data는 패들 주문 시 입력하는 "스티커 메모"입니다. 웹후크가 다시 돌아오면 백엔드는 이 메모를 사용하여 이 결제가 어떤 보고 및 결제 세션에 해당하는지 파악합니다.

10단계: 웹훅만 보고서 잠금을 해제하도록 허용

【이 단계의 핵심】단지 사용자가 페이지로 돌아오거나 URL에 더 많은 매개변수가 있거나 프런트엔드 표시가 성공했다는 이유만으로 직접 잠금을 해제하지 마세요.

Paddle은 백엔드에 다음을 알립니다.

POST /api/webhooks/패들

백엔드는 다음 사항을 확인해야 합니다.

  1. 원시 본체로 Paddle-Signature를 확인합니다.
  2. transaction.completed만 허용됩니다.
  3. custom_data.payment_session_id를 확인하세요.
  4. custom_data.report_id를 확인하세요.
  5. 가격ID를 확인하세요.
  6. 금액을 확인하세요.
  7. 통화를 확인하세요.
  8. 반복되는 웹후크는 멱등원이어야 합니다.
  9. 모든 점검을 통과한 후에만 accessToken를 작성하십시오.

Codex에 대한 팁 단어:

POST /api/webhooks/paddle을 구현하세요.

요구사항:
1. 패들시그니처 확인을 위해 반드시 생바디를 사용해야 합니다.
2. 거래 완료 잠금 해제만 허용됩니다.
3. transaction.pay_failed / transaction.canceled / transaction.past_due는 잠금 해제되지 않습니다.
4. custom_data의 reportId 및 Payment_session_id는 로컬 세션과 일치해야 합니다.
5. 가격 ID, 금액, 통화가 일치하지 않으면 잠금 해제가 불가능합니다.
6. 반복된 웹훅 권한은 반복적으로 발급될 수 없습니다.
7. 모든 오류는 문제 해결을 용이하게 하기 위해 Payment_events에 기록되어야 합니다.
💡 왜 이러는 걸까요#
사용자의 결제 페이지가 귀하의 웹사이트로 다시 이동합니다. 이는 브라우저가 반환되었다는 의미일 뿐, 금액이 확인되었다는 의미는 아닙니다. 진정으로 신뢰할 수 있는 신호는 Paddle 서버에서 전송된 서명이 검증된 웹훅입니다.

샌드박스는 결제 플랫폼에서 제공하는 테스트 환경입니다. 실제로 돈을 모으지 않고도 API, 웹훅, 잠금 해제 로직이 올바른지 확인할 수 있습니다.

샌드박스와 라이브는 서로 다른 세계입니다. 샌드박스 키는 실제 돈을 받을 수 없으며 라이브 키를 무작위 테스트에 사용해서는 안 됩니다. 전환 시 키, 가격 ID, 웹훅 비밀번호가 혼합되지 않도록 세트로 교체하세요.

[이 장의 핵심] 사용자가 실제로 지불했음을 증명할 수 있어야 하며 보고서는 백엔드에 의해 자동으로 잠금 해제됩니다.

완료 후 항목별로 확인해주세요.

  1. 사용자가 결제 버튼을 클릭하여 Paddle 결제를 엽니다.
  2. Paddle sandbox가 결제한 후 웹훅이 Zeabur 백엔드로 돌아갑니다.
  3. 백엔드는 transaction.completed 이후에만 잠금 해제됩니다.
  4. 잘못된 서명은 잠금 해제되지 않습니다.
  5. 잘못된 금액은 잠금 해제되지 않습니다.
  6. 잘못된 가격 ID는 잠금 해제되지 않습니다.
