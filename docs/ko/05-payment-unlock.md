# 05. 도메인 이름을 얻은 후 패들 결제를 수락하고 자동으로 잠금을 해제하세요.

![패들 결제 잠금 해제 챕터 아트](../../assets/chapters/chapter-05-paddle.webp)
이 장에서는 사용자가 이전 장을 완료하고 HTTPS 도메인 이름을 얻었다고 가정합니다. 예:

```text
https://your-project.zeabur.app
```

**【이 장의 핵심】Zeabur 도메인 이름을 사용하여 Paddle 설정을 완료한 다음 백엔드가 Paddle 웹훅을 통해 보고서를 자동으로 잠금 해제하도록 합니다. **

이 장은 코드로 시작하지 않고 먼저 Paddle이 백그라운드에서 필요로 하는 것들을 완성합니다.

> 💡 **왜 이러는 걸까요#  **
> 패들은 단지 버튼만 제공하는 것이 아닙니다. 계정, 제품, 도메인, 결제 페이지, 알림 주소를 확인합니다. 백그라운드 데이터가 완성되지 않은 경우, 코드를 올바르게 작성하더라도 `checkout not enabled` 등의 오류가 발생할 수 있습니다.

### 1단계: 먼저 전체 링크에서 Paddle이 수행하는 작업을 이해합니다.

**【이 단계의 핵심】Paddle은 돈을 모으고 지불 결과를 알리는 역할을 담당하며 웹 사이트는 주문 생성 및 보고서 잠금 해제를 담당합니다. **

전체 프로세스는 다음과 같습니다.

```text
사용자가 클릭하여 잠금 해제
  -> 귀하의 웹사이트 백엔드가 결제 세션을 생성합니다.
  -> 백엔드는 Paddle에게 결제 생성을 요청합니다.
  -> 사용자는 Paddle 페이지에서 결제합니다.
  -> Paddle은 웹후크를 사용하여 백엔드에 알립니다.
  -> 백엔드는 결제가 유효한지 확인합니다.
  -> 백엔드 잠금해제 해당 reportId
```

귀하의 웹사이트는 다음 세 가지 작업을 수행해야 합니다.

1. 결제를 생성합니다.
2. 웹훅을 수신하고 확인합니다.
3. 결제 확인 후 접근 권한이 부여됩니다.

패들은 세 가지 일을 합니다:

1. 결제 페이지를 표시합니다.
2. 일부 지역에서는 신용카드, PayPal 또는 현지 결제 수단을 사용하여 처리합니다.
3. 결제 결과를 백엔드로 다시 보냅니다.

> 💡 **왜 이러는 걸까요#  **
> 사용자 결제는 프론트엔드 웹페이지에 맡겨져 판단할 수 없습니다. 프런트 엔드는 매장 디스플레이 영역과 같고, 백 엔드는 계산원 시스템과 같으며, Paddle은 제3자 계산대와 같습니다. 계산대가 백엔드에 "금액이 확인되었습니다"라고 통보한 경우에만 백엔드가 문을 열고 보고서를 전달해야 합니다.

### 2단계: 패들 온보딩 완료

**【이 단계의 핵심】먼저 결제를 생성할 수 있는 Paddle 계정을 만드세요. **

Paddle 백엔드를 입력하고 필요에 따라 다음 페이지를 채우십시오.

1. 계정 또는 회사 정보.
2. 판매하는 제품의 유형.
3. 제품 설명.
4. 연소득 범위.
5. 결제방법
6. 웹사이트 도메인 이름.
7. Paddle의 허용 가능한 사용 정책을 준수합니다.

제품 설명은 다음과 같이 보수적이고 명확하게 작성할 수 있습니다.

```text
일회성 디지털 경력 평가 보고서를 판매합니다.
사용자는 퀴즈를 풀고 맞춤형 온라인 보고서를 받습니다.
이 제품은 취업 알선, 재정 조언, 의료 조언 또는 직업 결과 보장이 아닌 디지털 콘텐츠 액세스입니다.
```

패들이 표시되는 경우:

```text
이 계정에 대한 Checkout이 아직 활성화되지 않았습니다.
```

우선순위 확인:

1. Onboarding 완료 여부.
2. 홈페이지 승인이 완료되었나요?
3. 기본 결제 링크 설정 여부.
4. 상품 및 가격의 유무.
5. 계정이 아직 Paddle 검토를 기다리고 있나요?
> 💡 **왜 이러는 걸까요#  **
> 이 단계는 캐셔를 오픈하기 위한 가맹점 리뷰와 같습니다. Paddle은 귀하가 판매하는 제품, 사용자가 구매하는 제품, 플랫폼 정책을 준수하는지 여부를 알아야 합니다. 이는 단순한 기술 API가 아닙니다.

### 3단계: 웹사이트 인증 제출

**[이 단계의 핵심] 이전 장에서 얻은 Zeabur 도메인 이름을 Paddle에 입력하고 이것이 귀하의 판매 웹사이트인지 Paddle이 확인하도록 합니다. **

Paddle의 웹사이트 승인 또는 도메인 확인 페이지에서 다음을 입력하세요.

```text
https://your-zeabur-도메인 이름
```Paddle에 가격 페이지가 필요한 경우 다음을 입력하세요.

```text
https://도메인/가격
```Paddle에 약관, 개인 정보 보호 및 환불이 필요한 경우 다음을 각각 입력하세요.

```text
https://도메인/약관
https://도메인/개인정보
https://도메인/환불
```

이러한 URL은 직접 열 수 있어야 하며 웹사이트 홈페이지만 채울 수는 없습니다.

![패들 웹사이트 확인 지침](../../assets/diagrams/04-paddle-domain.svg)

> 💡 **왜 이러는 걸까요#  **
> Paddle은 가격이 어디에 있는지, 규칙이 어디에 있는지, 개인 정보 보호 지침이 어디에 있는지, 환불 지침이 어디에 있는지 등 사용자의 관점에서 웹사이트를 살펴봐야 합니다. 전체 경로가 포함된 URL은 홈페이지보다 전달하기가 더 쉽습니다.

### 4단계: 기본 결제 링크 설정

**[이 단계의 핵심] Tell Paddle: 나중에 결제를 생성할 때 결제 페이지에 어떤 확인된 도메인 이름을 사용해야 하는지. **

기본 결제 링크를 작성하는 것이 좋습니다:

```text
https://your-zeabur-domain/
```

여기서 흔히 저지르는 오해:

1. 사용자에게 게시하려는 제품 링크가 아닙니다.
2. 웹훅 URL이 아닙니다.
3. 특정 ReportId에 대한 결과페이지가 아닙니다.
4. Paddle이 결제 생성 시 사용하는 계정 수준의 결제 도메인 이름입니다.

기본 결제 링크가 설정되지 않은 경우 API 키가 정확하더라도 백엔드에서 거래 결제를 생성하지 못할 수 있습니다.

> 💡 **왜 이러는 걸까요#  **
> 기본 결제 링크는 '결제 시스템에서 기본적으로 사용하는 매장 주소'라고 생각하시면 됩니다. 이 주소가 없으면 Paddle은 결제 페이지를 호스팅할 승인된 웹사이트를 알 수 없습니다.

### 5단계: 일회성 제품 만들기

**【이 단계의 핵심】Paddle에서 판매하려는 디지털 리포팅 제품을 만듭니다. **

다음을 작성하는 것이 좋습니다.

| 필드 | 추천 글쓰기 |
| --- | --- |
| 제품명 | AI 경력 활동 보고서 또는 보고서 이름 |
| 설명 | 개인화된 디지털 경력 평가 보고서에 대한 일회성 액세스. |
| 제품 유형 | 디지털 제품 |
| 세금 카테고리 | 디지털 상품, eBook 또는 현재 귀하의 Paddle 계정에 허용되는 가장 가까운 카테고리 |

제품이 실제로 월별 요금을 청구하지 않는 한 구독이나 장기 멤버십으로 작성하지 마십시오.

> 💡 **왜 이러는 걸까요#  **
> 제품은 "당신이 판매하는 것"입니다. 일회성 보고서의 경우 제품은 수업, 직업 서비스 또는 인적 컨설팅 약속이 아닌 디지털 콘텐츠에 대한 일회성 액세스여야 합니다.

### 6단계: 일회성 가격 2개 생성

**【이 단계의 핵심】동일 제품에 대해 국내 및 해외 두 가지 일회성 가격을 설정합니다. **

먼저 빌드하는 것이 좋습니다:

| 목적 | 통화 및 가격 | 설명 |
| --- | --- | --- |
| 국내 가격 | 9.90위안 | 중국 지역 또는 중국 사용자를 위한 |
| 해외 가격 | USD 1.99 | 해외 신용카드/PayPal 사용자를 위한 |

가격 유형 선택:

```text
일회성
```

구독을 선택하지 마세요.

생성 후 두 개의 가격 ID를 복사합니다.```bash
PADDLE_CNY_PRICE_ID=pri_xxx
PADDLE_USD_PRICE_ID=pri_xxx
```

![패들 제품 및 가격 설명](../../assets/diagrams/05-paddle-product-price.svg)

> 💡 **왜 이러는 걸까요#  **
> 상품은 상품 그 자체이며, 가격은 해당 상품의 일정한 판매가격입니다. 제품에는 RMB 가격, USD 가격 등 여러 가격이 있을 수 있습니다. 백엔드가 결제를 생성할 때 가격 ID를 사용하여 이번에 청구해야 하는 금액을 Paddle에 알려줍니다.

### 7단계: API 키를 생성하고 Zeabur 변수에 넣습니다.

**【이 단계의 핵심】API 키는 백엔드에서만 사용되며 프런트엔드 공개 파일에 넣어서는 안 됩니다. **

Paddle 개발자 도구에서 API 키를 만듭니다.

그런 다음 Zeabur의 변수를 입력하고 다음을 입력합니다.```bash
PADDLE_ENVIRONMENT=sandbox
PADDLE_API_KEY=你的_sandbox_api_key
PADDLE_CNY_PRICE_ID=pri_xxx
PADDLE_USD_PRICE_ID=pri_xxx
```

참고:

1. 샌드박스 키는 샌드박스 가격과 일치합니다.
2. 라이브 키는 라이브 가격과 쌍을 이룹니다.
3. 섞지 마세요.
4. `public/monetization.json`에 API 키를 쓰지 마십시오.
5. 프런트 엔드 `.tsx`, `.js` 및 `.html`에 API 키를 쓰지 마십시오.

올바른 개념은 다음과 같습니다.

```text
브라우저 프런트 엔드: "결제하고 싶습니다"만 알 수 있습니다.
백엔드: 결제를 생성하려면 API 키를 Paddle로 가져가세요.
패들: 결제 페이지 URL로 돌아가기
```

> 💡 **왜 이러는 걸까요#  **
> API 키는 결제 백엔드 키와 같습니다. 사용자의 브라우저는 공개된 장소이므로 프런트 엔드에 있는 모든 항목이 표시될 수 있습니다. 키는 백엔드 또는 배포 플랫폼의 환경 변수에만 배치될 수 있습니다.

### 8단계: 웹훅 설정

**【이 단계의 핵심】결제가 완료된 후 웹사이트에 통보할 주소를 Paddle에 알려주세요. **

패들 알림 대상을 입력하세요.

```text
https://your-zeabur-domain/api/webhooks/paddle
```

최소한 다음 이벤트를 선택하세요.

```text
거래.완료
거래.결제_실패
거래.취소됨
transaction.past_due
```

그런 다음 웹훅 비밀을 복사하고 Zeabur 변수에 입력합니다.```bash
PADDLE_WEBHOOK_SECRET=你的_webhook_secret
PADDLE_ALLOW_UNSIGNED_WEBHOOKS=false
```

![패들 웹훅 신호](../../assets/diagrams/06-paddle-webhook.svg)

> 💡 **왜 이러는 걸까요#  **
> 웹훅은 Paddle이 적극적으로 백엔드에 "이 트랜잭션이 완료되었습니다."라고 호출하는 것과 같습니다. 웹훅 비밀은 양측이 합의한 비밀번호와 같습니다. 비밀번호가 없으면 누군가 가짜 전화를 걸어 돈을 지불했다고 말할 수도 있습니다.

### 9단계: 백엔드에서 Paddle 체크아웃을 생성하도록 허용

**[이 단계의 핵심] 사용자가 결제 버튼을 클릭하면 프런트엔드에서는 백엔드만 요청하고 Paddle API 키에는 직접 접속하지 않습니다. **

프런트엔드 요청:```http
POST /api/payments/checkout
Content-Type: application/json

{
  "reportId": "rep_xxx",
  "region": "domestic"
}
```

백엔드는 다음을 수행해야 합니다.

1. 로컬 결제 세션을 생성하세요.
2. 지역에 따라 `PADDLE_CNY_PRICE_ID` 또는 `PADDLE_USD_PRICE_ID`를 선택하세요.
3. Paddle 생성 트랜잭션 API를 호출합니다.
4. `reportId`를 `custom_data`에 넣습니다.
5. `payment_session_id`를 `custom_data`에 넣습니다.
6. Paddle 거래 ID를 저장하세요.
7. Paddle 체크아웃 URL을 프런트 엔드로 반환합니다.

Codex에 대한 팁 단어:

```text
이미 Zeabur HTTPS 도메인 이름이 있고 이제 Paddle에 연결하고 싶습니다.

새 패들 공급자를 추가하세요.

요구사항:
1. 테스트를 용이하게 하기 위해 모의 공급자를 유지하십시오.
2. POST /api/paids/checkout은 Paddle 생성 트랜잭션을 호출합니다.
3. 국내에서는 PADDLE_CNY_PRICE_ID, 해외에서는 PADDLE_USD_PRICE_ID를 사용하세요.
4. 거래 custom_data에는 reportId 및 Payment_session_id가 포함되어야 합니다.
5. 모든 비밀은 process.env에서만 읽을 수 있습니다.
6. public/monetization.json에는 비밀이 포함될 수 없습니다.
```

> 💡 **왜 이러는 걸까요#  **
> `custom_data`는 패들 주문 시 입력하는 "스티커 메모"입니다. 웹후크가 다시 돌아오면 백엔드는 이 메모를 사용하여 이 결제가 어떤 보고 및 결제 세션에 해당하는지 파악합니다.

### 10단계: 웹훅만 보고서 잠금을 해제하도록 허용

**【이 단계의 핵심】단지 사용자가 페이지로 돌아오거나 URL에 더 많은 매개변수가 있거나 프런트엔드 표시가 성공했다는 이유만으로 직접 잠금을 해제하지 마세요. **

Paddle은 백엔드에 다음을 알립니다.

```text
POST /api/webhooks/패들
```

백엔드는 다음 사항을 확인해야 합니다.

1. 원시 본체로 `Paddle-Signature`를 확인합니다.
2. `transaction.completed`만 허용됩니다.
3. `custom_data.payment_session_id`를 확인하세요.
4. `custom_data.report_id`를 확인하세요.
5. 가격ID를 확인하세요.
6. 금액을 확인하세요.
7. 통화를 확인하세요.
8. 반복되는 웹후크는 멱등원이어야 합니다.
9. 모든 점검을 통과한 후에만 `accessToken`를 작성하십시오.

Codex에 대한 팁 단어:

```text
POST /api/webhooks/paddle을 구현하세요.

요구사항:
1. 패들시그니처 확인을 위해 반드시 생바디를 사용해야 합니다.
2. 거래 완료 잠금 해제만 허용됩니다.
3. transaction.pay_failed / transaction.canceled / transaction.past_due는 잠금 해제되지 않습니다.
4. custom_data의 reportId 및 Payment_session_id는 로컬 세션과 일치해야 합니다.
5. 가격 ID, 금액, 통화가 일치하지 않으면 잠금 해제가 불가능합니다.
6. 반복된 웹훅 권한은 반복적으로 발급될 수 없습니다.
7. 모든 오류는 문제 해결을 용이하게 하기 위해 Payment_events에 기록되어야 합니다.
```

> 💡 **왜 이러는 걸까요#  **
> 사용자의 결제 페이지가 귀하의 웹사이트로 다시 이동합니다. 이는 브라우저가 반환되었다는 의미일 뿐, 금액이 확인되었다는 의미는 아닙니다. 진정으로 신뢰할 수 있는 신호는 Paddle 서버에서 전송된 서명이 검증된 웹훅입니다.

### 11단계: 고정된 순서로 샌드박스 테스트

**[이 단계의 핵심] 먼저 샌드박스를 사용하여 전체 링크가 통과할 수 있는지 확인한 다음 라이브로 전환합니다. **

다음으로 다음 순서로 테스트하세요.

1. Zeabur 환경 변수에 대한 샌드박스 API 키를 입력합니다.
2. Zeabur 환경 변수에 샌드박스 가격 ID를 입력합니다.
3. 샌드박스 웹훅 비밀로 Zeabur 환경 변수를 입력합니다.
4. 재배포.
5. 온라인 도메인 이름을 엽니다.
6. 퀴즈를 완성하세요.
7. 결제를 클릭하세요.
8. Paddle 샌드박스 체크아웃으로 이동합니다.
9. 패들에서 제공하는 테스트 카드로 결제하세요.
10. Paddle 알림 로그를 엽니다.
11. Zeabur 로그를 엽니다.
12. 웹훅이 성공적으로 반환되는지 확인합니다.
13. 신고 페이지로 돌아가서 자동 잠금 해제를 확인하세요.

> 💡 **왜 이러는 걸까요#  **
> 샌드박스는 결제 플랫폼에서 제공하는 테스트 환경입니다. 실제로 돈을 모으지 않고도 API, 웹훅, 잠금 해제 로직이 올바른지 확인할 수 있습니다.

### 12단계: 일반적인 오류 문제 해결

**【이 단계의 핵심】오류가 표시되면 먼저 계정 설정, 환경 변수, 코드 또는 웹훅 문제인지 확인하세요. **

#### Checkout이 아직 활성화되지 않았습니다.

우선순위 확인:

1. 패들 온보딩 완료 여부.
2. 홈페이지 인증 통과 여부.
3. 기본 결제 링크 설정 여부.
4. 상품 및 가격의 설정 여부.
5. 계정이 아직 Paddle에서 검토 중인지 여부.

#### 인증 헤더 형식이 잘못되었습니다.

환경 변수에는 키 자체만 포함됩니다.```bash
PADDLE_API_KEY=pdl_sdbx_xxx
```

요청 헤더는 다음과 같습니다.

```text
승인: 베어러 pdl_sdbx_xxx
```

환경 변수에 쓰지 마십시오:```bash
PADDLE_API_KEY=Bearer pdl_sdbx_xxx
```

#### 결제 후 잠금이 해제되지 않음

순서대로 확인하세요:

1. Paddle 알림 로그가 웹훅을 보내나요?
2. Zeabur 로그가 요청을 받았습니까?
3. Webhook URL이 `/api/webhooks/paddle`인지 여부.
4. Webhook 비밀이 일관성이 있는지 여부.
5. 이벤트가 `transaction.completed`인가요?
6. `custom_data`에는 `payment_session_id` 및 `report_id`가 있습니다.
7. `/data/payment-store.json`가 성공적으로 작성되었는지 여부.

> 💡 **왜 이러는 걸까요#  **
> 결제실패는 동일한 사유로 발생하지 않을 수 있습니다. 질문을 "Paddle이 알림을 보냈는지, Zeabur가 알림을 받았는지, 백엔드가 확인을 통과했는지, 데이터가 기록되었는지"로 분할하면 어느 섹션이 멈췄는지 빠르게 찾을 수 있습니다.

### 13단계: 라이브로 전환하기 전 최종 확인

**【이 단계의 핵심】Sandbox가 실행된 후 Paddle의 라이브 데이터를 교체합니다. **

실시간으로 전환하기 전에 확인하세요.

1. 패들 라이브 온보딩을 통과했습니다.
2. 라이브 홈페이지 승인이 완료되었습니다.
3. 라이브 기본 결제 링크가 설정되었습니다.
4. 라이브 상품이 생성되었습니다.
5. 실시간 일회성 가격이 설정되었습니다.
6. Zeabur 변수가 라이브 API 키로 대체되었습니다.
7. Zeabur 변수가 실시간 가격 ID로 대체되었습니다.
8. Zeabur 변수가 라이브 웹훅 비밀로 대체되었습니다.
9. `PADDLE_ENVIRONMENT=live`.
10. 시험 입구, 0위안 잠금 해제, 모의 버튼이 모두 닫힙니다.

> 💡 **왜 이러는 걸까요#  **
> 샌드박스와 라이브는 서로 다른 세계입니다. 샌드박스 키는 실제 돈을 받을 수 없으며 라이브 키를 무작위 테스트에 사용해서는 안 됩니다. 전환 시 키, 가격 ID, 웹훅 비밀번호가 혼합되지 않도록 세트로 교체하세요.

### 이 장의 완료 기준

**[이 장의 핵심] 사용자가 실제로 지불했음을 증명할 수 있어야 하며 보고서는 백엔드에 의해 자동으로 잠금 해제됩니다. **

완료 후 항목별로 확인해주세요.

1. 사용자가 결제 버튼을 클릭하여 Paddle 결제를 엽니다.
2. Paddle sandbox가 결제한 후 웹훅이 Zeabur 백엔드로 돌아갑니다.
3. 백엔드는 `transaction.completed` 이후에만 잠금 해제됩니다.
4. 잘못된 서명은 잠금 해제되지 않습니다.
5. 잘못된 금액은 잠금 해제되지 않습니다.
6. 잘못된 가격 ID는 잠금 해제되지 않습니다.
7. 중복된 Webhook은 반복적으로 발행되지 않습니다.
8. 사용자는 보고서 페이지를 새로 고친 후에도 잠금 해제된 콘텐츠를 계속 볼 수 있습니다.
9. 브라우저를 변경하거나 액세스 토큰이 없으면 다른 사람의 전체 보고서를 볼 수 없습니다.

이 모든 것이 확립되면 패들 액세스는 정말 성공적입니다.
