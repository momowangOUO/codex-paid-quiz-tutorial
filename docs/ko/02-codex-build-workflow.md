# 02. Codex가 0에서 웹사이트 구축을 도와주는 방법

![Codex 빌드 워크플로우 챕터 아트](../../assets/chapters/chapter-02-codex.webp)
**[이 장의 핵심] 웹 사이트 구축 작업을 여러 개의 작은 라운드로 나누고 각 라운드에서 허용 가능한 작업을 Codex에 요청하십시오. **

이 장에서는 한 가지에 대해서만 설명합니다. **웹 사이트 작성 방법을 모를 때 Codex에 명령을 내리는 방법. **

“완전한 상업용 웹사이트를 구축할 수 있게 도와주세요.”라고 말하면서 시작하지 마세요. 이 범위는 너무 크고 코덱스는 한 번에 너무 많이 변경되기 쉽습니다. 웹사이트를 수용할 수 있는 일련의 작은 작업으로 나누어야 합니다.

> 💡 **왜 이러는 걸까요#  **
> Codex는 작은 작업을 처리할 때 더 안정적입니다. 한꺼번에 "건물 전체를 지어주세요"라고 말하는 것이 아니라, 건설 파트너에게 공사를 해달라고 부탁하는 것보다 먼저 기초를 확인한 다음 벽을 쌓은 다음 물과 전기를 연결하는 것과 같다고 생각하시면 됩니다.

## 먼저 코덱스에게 어떤 제품을 만들고 싶은지 알려주세요

**【이 섹션의 핵심】 먼저 Codex가 제품 목표와 제한 사항을 이해할 수 있도록 완전한 프롬프트 단어를 사용하십시오. **

이 단락을 첫 번째 프롬프트로 복사하세요.

```text
유료퀴즈사이트를 만들겠습니다.

대상 사용자는 다음을 수행합니다.
1. 홈페이지를 엽니다.
2. 시험 문제 세트를 완성하세요
3. 보고서의 무료 소개 버전을 확인하세요
4. 결제 버튼 클릭
5. 결제가 완료되면 전체 보고서가 자동으로 잠금 해제됩니다.

먼저 사용 가능한 최소 버전을 만드는 데 도움을 주세요.
요구사항:
- React + Vite를 이용한 프론트엔드
- Node.js를 사용한 백엔드
- 모의결제를 먼저 사용하고, 실제 패들은 받지 않습니다.
- 로그인 계정이 필요하지 않습니다
- 프론트엔드에 어떤 비밀도 넣지 마세요
- 모든 단계에서 로컬로 실행하고 검증하는 방법을 알려주세요.
```

이미 프로젝트가 있으면 다음을 추가하세요.

```text
먼저 기존 프로젝트 구조를 읽고 프로젝트를 다시 빌드하지 마십시오. 기존 코딩 스타일을 고수하려고 노력하세요.
```

## 처음 만들 때, 만드는 것들은 작아야 합니다.

**[이 섹션의 핵심] 첫 번째 버전은 프로세스를 실행할 수 있는 가장 작은 웹사이트만 구축합니다. **

첫 번째 버전에는 다음 페이지만 필요합니다.

| 페이지 | 목적 | 최소 요구사항 |
| --- | --- | --- |
| 홈페이지 | 사용자가 퀴즈를 시작하도록 허용 | 제목, 시작 버튼 |
| 답변 페이지 | 답변 수집 | 최소 3-5개의 시험 문제, 나중에 확장 |
| 무료 결과 페이지 | 신뢰 구축 | 부분적인 분석은 표시하지만 전체 경력 답변은 표시하지 않음 |
| 페이월 | 잠금 해제용 부트스트랩 | 하나의 결제 버튼, 하나의 대기 상태 |
| 전체 보고서 페이지 | 확인 잠금 해제 | 모의결제 후 전체 내용 보기 |

아직 요청하지 마세요.

- 다국어.
- 아름다운 애니메이션.
-백엔드 관리.
- PDF/긴 이미지 저장.
- 진짜 패들.
- 문제은행을 완성하세요.

나중에 모두 추가할 수 있습니다. 첫 번째 단계는 프로세스가 원활하게 진행되는 한입니다.

> 💡 **왜 이러는 걸까요#  **
> 최소 버전은 최종 제품은 아니지만 해당 경로가 실현 가능함을 증명하는 데 사용됩니다. 경로가 구현되면 시각적, 다국어, 보고서 저장 및 실제 결제를 추가하여 더욱 안정적이 될 것입니다.

## 권장 프로젝트 구조

**【이 섹션의 핵심】프런트엔드, 백엔드, 데이터 및 구성을 분리하려면 Codex가 사전에 필요합니다. **

다음 구조에 따라 Codex를 구축하도록 요청할 수 있습니다.

```text
유료 퀴즈 사이트/
  소스/
    앱/
      앱.tsx
    구성요소/
    데이터/
      질문.ts
    수익화/
      config.ts
    스타일/
      전역.css
  서버/
    지불 서버.mjs
  공개/
    수익화.json
  패키지.json
  .env.지불.예
```

각 디렉토리의 의미:

| 목차 | 목적 |
| --- | --- |
| `src/app` | 페이지 흐름 |
| `src/components` | 버튼, 카드, 질문, 보고서 모듈 |
| `src/data` | 질문, 결과 유형, 샘플 보고서 자료 |
| `src/monetization` | 프런트 엔드에서 공개 유료 구성 읽기 |
| `server` | 백엔드 API, 결제 세션, 웹훅 |
| `public` | 브라우저에 노출될 수 있는 파일 |

초보자가 저지르는 가장 흔한 실수는 모든 것을 하나의 파일에 밀어넣는 것입니다. 코덱스를 디렉토리별로 분할하면 나중에 관리하기가 더 쉬워집니다.

> 💡 **왜 이러는 걸까요#  **
> 프로젝트 구조는 보관 캐비닛과 같습니다. 제목, 페이지, 스타일, 결제 인터페이스가 각자의 위치에 배치되어 나중에 특정 부분을 수정해야 할 때 큰 파일을 뒤질 필요가 없습니다.

## 1라운드: 퀴즈만 진행

**[이 섹션의 핵심] 먼저 사용자가 홈페이지에서 결과 페이지까지의 질문에 답변할 수 있는지 확인합니다. **

코덱스에:

```text
먼저 기본 테스트 과정을 완료하고 결제를 수락하지 마세요.

요구사항:
- 홈페이지에 "Start Quiz"가 있습니다.
- 답변 페이지에는 한 번에 하나의 질문이 표시됩니다.
- 사용자는 답변을 선택한 후 다음 질문으로 이동할 수 있습니다.
- 답변 후 ReportId 생성
- 결과 페이지로 이동
- 결과 페이지에는 무료 소개와 "전체 보고서 잠금 해제" 버튼이 표시됩니다.

다음 정보도 제공하세요.
- npm 스크립트
- 로컬 작동 모드
- 최소한의 테스트 방법
```

수락:```bash
npm install
npm run dev
```

현지 웹사이트를 열고 직접 답변해보세요. 비전을 바꾸려고 서두르지 말고, 먼저 그 길이 완성될 수 있는지 확인하세요.

## 2라운드: 백엔드에서 결제 상태를 저장하도록 허용

**【이 섹션의 핵심】프런트엔드가 스스로 결정하도록 두지 않고 결제 상태를 백엔드에 맡겨서 저장하세요. **

코덱스에:

```text
이제 Node 백엔드를 추가하고 먼저 모의결제를 해보세요.

백엔드 API:
- POST /api/결제/체크아웃
  ReportId 수신, 결제 세션 생성, sessionId 및 checkoutUrl 반환

- GET /api/결제/세션/:id
  반품 보류 중/결제 완료/실패

- POST /api/결제/mock-complete
  로컬 테스트의 경우에만 세션을 유료로 표시하세요.

데이터는 먼저 JSON 파일에 저장될 수 있습니다.
보고서 잠금을 해제하기 위해 프런트엔드가 URL 매개변수에만 의존할 수 없는지 확인하세요.
```

수락:

- 결제가 이루어지지 않으면 전체 보고서를 볼 수 없습니다.
- 모의 완료 후 잠금해제 가능합니다.
- 페이지를 새로 고친 후에도 백엔드는 보고서가 잠금 해제되었는지 여부를 계속 알 수 있습니다.

## 3차: 페이월 스위치 추가

**【이 섹션의 핵심】공개 구성을 사용하여 페이월 스위치를 제어하여 개발 및 사전 출시 테스트를 용이하게 합니다. **

코덱스에:

```text
페이월을 켜고 끌 수 있도록 public/monetization.json을 추가하세요.

기본값:
{
  "활성화됨": 거짓,
  "checkoutMode": "API",
  "apiBaseUrl": "/api",
  "공급자": "모의"
}

요구사항:
- 활성화=false일 경우 개발 및 테스트가 편리하며 전체 보고서를 직접 볼 수 있습니다.
- 활성화=true인 경우 잠금 해제 전 결제가 이루어져야 합니다.
- 공개 파일에는 API 키나 비밀이 포함될 수 없습니다.
```

라이브로 전환하기 전에 계속해서 테스트를 수행하게 되므로 이 단계는 중요합니다. 스위치가 없으면 사용자에게 설익은 페이월을 쉽게 적용할 수 있습니다.

## 4라운드: 먼저 GitHub에 업로드 준비

**【이 섹션의 핵심】 업로드하기 전에 Codex가 창고의 보안 및 `.gitignore`를 확인하도록 하세요. **

로컬 모의 프로세스가 실행된 후 먼저 프로젝트를 GitHub에 업로드하기에 적합한 상태로 구성합니다.

코덱스에:

```text
이 프로젝트가 GitHub에 업로드하기에 적합한지 확인해주세요.

요구사항:
- .gitignore는 .env, .env.*, *.local, node_modules, dist, 로그 및 임시 파일을 무시해야 합니다.
- 프로젝트를 스캔하여 Paddle API 키, 웹훅 비밀 또는 관리자 토큰이 없는지 확인하세요.
- README를 통해 다른 사람들이 프로젝트의 목적을 이해할 수 있는지 확인
- GitHub에 처음 업로드할 때 실행할 git 명령을 알려주세요.
- 비밀이 발견되면 파일 경로를 나열하고 해당 키를 취소하거나 교체하도록 알려주세요.
```

수락하는 동안 GitHub 저장소에서 프로젝트 파일을 볼 수 있어야 하지만 `.env`, `.env.payment.local` 또는 API 키는 볼 수 없습니다.

## 5라운드: Zeabur 배치 다시 준비

**【이 섹션의 핵심】Codex가 Zeabur가 구축하고 시작할 수 있는 형태로 프로젝트를 구성하도록 합니다. **

GitHub 저장소가 준비된 후에는 아직 Paddle을 선택하려고 서두르지 마세요. Paddle은 나중에 웹사이트 도메인 이름을 입력하고 확인하도록 요청하며, 열 수 있는 HTTPS 도메인 이름을 사용하려면 기본 결제 링크도 요구합니다.

따라서 올바른 순서는 다음과 같습니다.

```text
로컬 모의 실행 -> GitHub에 업로드 -> Zeabur에 배포 -> HTTPS 도메인 이름 가져오기 -> Paddle 설정
```

코덱스에:

```text
이 프로젝트를 Zeabur에 배포할 수 있는 구조로 구성해 주세요.

요구사항:
- npm run build는 프런트엔드 dist를 생성할 수 있습니다.
- npm run start는 동일한 Node 서비스를 시작할 수 있습니다.
- 노드 서비스는 dist 정적 파일과 /api/*를 모두 제공해야 합니다.
- 서버는 process.env.PORT를 수신해야 합니다.
- 호스트는 0.0.0.0을 사용합니다.
- 비밀을 유출하지 않고 /api/health를 추가했습니다.
- .env, .local, node_modules, dist 및 로컬 데이터 파일을 GitHub에 제출하지 마세요.
- 아직 패들 키를 요청하지 마세요. 이제 검증 가능한 HTTPS 도메인 이름만 얻으려고 하기 때문입니다.

다음 사항도 알려주십시오.
1. GitHub에 어떤 파일을 제출해야 합니까?
2. Zeabur의 빌드 명령 및 시작 명령
3. Zeabur에서는 어떤 변수를 먼저 설정해야 합니까?
4. 웹사이트와 /api/health에 모두 접근 가능한지 확인하는 방법
```

이 단계가 완료되면 다음과 유사한 공식 URL이 생성됩니다.

```text
https://your-project.zeabur.app
```

그러면 이 URL은 Paddle의 웹사이트 확인, 가격 페이지, 기본 결제 링크 및 웹훅 URL로 채워집니다.

## 6라운드: HTTPS 도메인 이름을 얻은 후 모의를 Paddle로 대체

**[이 섹션의 핵심] Zeabur 도메인 이름을 얻은 후 Codex를 실제 Paddle에 연결합니다. **

Zeabur 웹사이트가 열리고 `/api/health`가 정상일 때까지 기다린 다음 Codex를 제공합니다.

```text
새 Paddle 공급자를 추가하되 모의 공급자는 유지하세요.

요구사항:
- Paddle 생성 트랜잭션 API를 사용하여 POST /api/결제/체크아웃
- 사용자 지역이나 버튼 선택에 따라 CNY 가격 / USD 가격을 사용합니다.
- custom_data에는 reportId 및 Payment_session_id가 포함되어야 합니다.
- POST /api/webhooks/paddle 추가
- 웹훅은 패들 서명을 확인해야 합니다.
- 거래만 수락하세요. 잠금 해제가 완료되었습니다.
- 반복적으로 전송할 때 웹훅은 멱등원이어야 합니다.
- 서명 오류, 금액 불일치, 가격 ID 불일치 등의 경우 잠금 해제가 불가능합니다.
```Codex가 구현된 후에는 이러한 필드가 구성된 위치를 나타내도록 해야 합니다.

```text
PADDLE_ENVIRONMENT
PADDLE_API_KEY
PADDLE_CNY_PRICE_ID
PADDLE_USD_PRICE_ID
PADDLE_WEBHOOK_SECRET
PUBLIC_BASE_URL
```

참고: `PUBLIC_BASE_URL`는 Zeabur에서 제공한 HTTPS 도메인 이름으로 채워야 합니다. 예:

```text
https://your-project.zeabur.app
```Paddle 웹훅 URL은 다음과 같습니다.

```text
https://your-project.zeabur.app/api/webhooks/paddle
```

## 7라운드: Codex가 활성화되기 전에 보안 검사를 수행하도록 합니다.

**[이 섹션의 핵심] Codex가 활성화되기 전에 결제, 키, 웹훅 및 배포 위험을 확인하도록 하세요. **

코덱스에:

```text
이 프로젝트가 출시하기에 적합한지 확인하시기 바랍니다.

확인해야 할 핵심 사항:
1. 공개 파일에 API 키, 웹훅 비밀, 관리자 토큰이 있나요?
2. 결제 잠금 해제는 백엔드에서만 확인할 수 있는지 여부
3. 웹훅이 검증되었나요?
4. 웹훅이 반복되면 권한이 반복적으로 부여되나요?
5. Zeabur가 PORT를 읽습니까?
6. /api/health 제공 여부

## Codex에 오류를 어떻게 보고해야 합니까?
**[이 섹션의 핵심] 오류를 보고할 때 조치, 현상, 예상 결과 및 로그를 제공해야 합니다. **

그냥 "깨졌다"고 말하지 마세요. 게시할 내용은 다음 4가지입니다.

```text
내가 한 일:
어떤 오류가 표시됩니까?
내가 기대하는 바는 다음과 같습니다.
관련 화면 설명 또는 로그:
```

예:

```text
Zeabur에서 웹사이트를 열면 502가 보입니다.

> "Broken"에는 위치 정보가 없습니다. 로그, 화면 상태, 방금 수행한 작업은 문제의 위치를 ​​파악하는 Codex의 단서입니다.
