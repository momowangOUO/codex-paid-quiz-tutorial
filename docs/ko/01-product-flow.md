# 01. 제품 프로세스를 세분화하는 방법

![제품 흐름 장 아트](../../assets/chapters/chapter-01-flow.webp)
**[이 장의 핵심] 코드를 작성하기 전에 먼저 "사용자가 보게 될 페이지, 각 단계에서 수행되는 작업, 백엔드가 필요한 단계"를 명확하게 분류하세요. **

코드 작성을 시작하기 전에 한 가지 질문에만 대답하면 됩니다.

```text
사용자는 사이트 접속부터 결제, 잠금 해제까지 어떤 화면을 거치게 되나요?
```

이 장에서는 아키텍처 다이어그램에 대해 설명하지 않지만 먼저 제품을 Codex가 이해할 수 있는 작은 작업으로 나눕니다.

> 💡 **왜 이러는 걸까요#  **
> Codex는 명확한 작업 경계를 요구합니다. 제품 프로세스는 로드맵과 같습니다. 먼저 사용자가 어디에 들어왔는지, 어디에서 질문에 답변하는지, 어디서 지불하는지, 어디에서 보고서를 읽는지 파악하여 나중에 코드를 작성할 때 여기저기서 보충하지 않아도 됩니다.

## 먼저 가장 짧은 사용자 경로를 그립니다.

**[이 섹션의 핵심] 먼저 홈페이지에서 전체 보고서까지 사용자를 위한 최단 경로를 작성합니다. **

유료 퀴즈 사이트로 가는 최단 경로는 다음과 같습니다:

```text
홈페이지
  -> 답변 페이지
  -> 무료 소개 보고서
  -> 결제 페이지
  -> 전체 보고서
  -> 보고서를 저장하거나 다시 엽니다.
```

아직 로그인할 필요는 없습니다. 저렴한 일회성 보고서에서 가장 중요한 것은 마찰을 줄이는 것입니다.

> 💡 **왜 이러는 걸까요#  **
> 로그인, 회원가입, 백엔드, 할인코드 모두 추후 추가 가능합니다. 첫 번째 버전에서는 더 많은 선반을 장식하기 전에 카운터가 실제로 돈을 모을 수 있는지 확인하는 것처럼 사용자가 전체 구매를 완료할 수 있습니다.

## 각 페이지에서 수행할 작업

**[이 섹션의 핵심] 첫 번째 버전이 너무 무거워지는 것을 방지하기 위해 각 페이지는 하나의 주요 작업만 담당합니다. **

### 홈

홈페이지는 사용자가 시작하도록 하는 역할만 담당합니다.

가지고 있어야 할 것:

- 이 퀴즈가 사용자가 해결하는 데 도움이 되는 문제를 설명하는 한 문장입니다.
- 시작 버튼.
- 선택사항: 언어 전환, 케이스 입력.

처음에 "결제하여 잠금 해제" 또는 "지금 구매"라고 쓰지 마세요. 사용자가 아직 시간을 투자하지 않았으며, 너무 일찍 돈을 인출하면 완료율이 낮아집니다.

### 답변 페이지

답변 페이지는 사용자가 질문을 완료할 수 있도록 하는 역할만 담당합니다.

가지고 있어야 할 것:

- 현재 문제 번호.
- 질문.
- 옵션.
- 이전 질문/다음 질문입니다.
- 진행 상황이 표시됩니다.
- 그림이나 시각 자료.

초보자는 먼저 5문제의 테스트 버전을 수행한 다음 프로세스를 통과한 후 48문제로 확장하는 것이 좋습니다.

### 무료 소개 보고서

무료 버전은 기분전환용도 아니고 공허한 이야기도 아닙니다. 사용자가 당신이 전문가라고 생각하게 만듭니다.

다음을 표시할 수 있습니다.

- 핵심 심리적 동인.
- 행동 경향과 잠재적인 정체 지점.
- 자기 인식과 외부 성과 사이의 격차.
- 전체 보고서는 어떤 방향으로 계속 분석할 것인가.

표시하지 않음:

- 직업 답변을 완료하세요.
- 전체 경로.
- 상세한 실행 계획.
- 저장할 수 있는 전체 보고서.

### 페이월

페이월은 사용자가 지불하는 것만 허용합니다.

가지고 있어야 할 것:

- 현재 가격.
- 명확한 결제 버튼.
- 결제 후 지침을 자동으로 잠금 해제합니다.
- 결제 실패 또는 보류 상태입니다.

한 번에 너무 많은 결제 방법 버튼을 입력하지 마세요. 백엔드는 지역에 따라 입구를 추천할 수 있습니다.

### 전체 보고서

완전한 보고서는 사용자가 "이것은 임의의 텍스트 조각이 아니다"라는 느낌을 주어야 합니다.

포함할 수 있는 것:

- 경력 레이더.
- 심리적 프로파일링.
- 적합한 직업 유형.
- 다양한 개발 경로.
- 위험 경계.
- 대체 방향.
- 보고서를 저장합니다.

## Codex에 양식 제출

**[이 섹션의 핵심] 페이지, 사용자 작업, 백엔드 참여 방법을 표로 정리한 후 Codex에 제출합니다. **

귀하의 제품 프로세스를 다음 표로 구성하고 Codex에 게시하십시오.

| 페이지 | 사용자에게 표시되는 내용 | 사용자가 할 수 있는 작업 | 백엔드가 관련되어야 하는가 |
| --- | --- | --- | --- |
| 홈 | 제품 설명, 시작 버튼 | 퀴즈 시작 | 필요하지 않음 |
| 답변 페이지 | 질문 및 옵션 | 답변, 다음 질문 | 실시간으로 저장하려는 경우가 아니면 필요하지 않음 |
| 무료 보고서 | 부분 분석, 잠금 해제 버튼 | 결제하려면 클릭하세요 | 결제 세션을 생성해야 합니다 |
| 패들 체크아웃 | 결제 양식 | 결제 | 패들 가공 |
| 전체 보고서 | 모든 분석 | 보기, 저장 | 확인 액세스 토큰이 필요합니다 |

## 보고서 ID란 무엇인가요?
**【이 섹션의 핵심】`reportId`는 특정 테스트 보고서의 번호입니다. **

`reportId`는 보고서의 번호입니다.

사용자가 질문에 대답한 후 프런트 엔드 또는 백 엔드는 `reportId`를 생성하고 모든 후속 작업은 이를 중심으로 진행됩니다.

```text
이 답변 -> 보고서 ID
이 주문 -> 신고 ID
이번에 잠금 해제 -> ReportId
이 전체 보고서 -> 보고서 ID
```

`reportId`가 없으면 결제 플랫폼에서 "누군가 지불했습니다"라고 알려주며 어떤 보고서를 잠금 해제해야 할지 알 수 없습니다.

> 💡 **왜 이러는 걸까요#  **
> `reportId`는 픽업번호와 같습니다. 사용자가 식사를 주문하고, 결제를 한 후, 식사를 받으러 돌아올 때에도 동일한 번호를 사용하여 동일한 내용에 해당해야 합니다.

## 결제 세션이란 무엇인가요?
**[이 섹션의 핵심] `payment_session`는 특정 결제 시도에 대한 기록입니다. **

`payment_session`는 결제 시도입니다.

사용자는 다음을 수행할 수 있습니다.

- 결제를 클릭하고 페이지를 닫습니다.
- 결제에 실패했습니다.
- 결제를 다시 시도하세요.
- 결제가 성공적으로 이루어졌으나 프런트 엔드가 되돌아오지 않습니다.

따라서 프런트엔드 상태에만 의존하지 마십시오. 저장할 백엔드:```json
{
  "sessionId": "pay_xxx",
  "reportId": "rep_xxx",
  "provider": "paddle",
  "providerOrderId": "txn_xxx",
  "status": "pending"
}
```

결제가 성공적으로 완료되면 다음으로 변경하세요.```json
{
  "status": "paid",
  "paidAt": "2026-05-28T00:00:00.000Z"
}
```

> 💡 **왜 이러는 걸까요#  **
> 보고서에는 여러 번의 결제 시도가 있을 수 있습니다. 사용자는 처음에는 결제 페이지를 닫을 수 있지만 두 번째에는 성공합니다. `payment_session`는 상태 혼란을 피하기 위해 이러한 시도를 별도로 기록할 수 있습니다.

## 액세스 토큰이란 무엇인가요?
**【이 섹션의 핵심】`accessToken`는 성공적인 결제 후 전체 보고서를 여는 열쇠입니다. **

`accessToken`는 보고를 완료하는 데 핵심입니다.

결제가 성공한 후 백엔드는 추측할 수 없는 토큰을 보고서에 보냅니다. 다음에 사용자가 돌아올 때 프런트 엔드는 백엔드에 토큰을 묻습니다.

```text
이 토큰에는 보고서 reportId를 볼 수 있는 권한이 있습니까?
```

전체 보고서는 백엔드에서 '예'라고 답한 후에만 표시됩니다.

> 💡 **왜 이러는 걸까요#  **
> 전체 보고서를 표시하려면 "누군가 이 보고서 ID에 대해 비용을 지불했습니다"에만 의존해서는 안 됩니다. 그렇지 않으면 다른 사람이 동일한 보고서 ID를 볼 수 있습니다. `accessToken`는 전용열쇠와 같아서, 열쇠를 가진 사람만이 열 수 있습니다.

## 첫 번째 버전에서는 아무것도 할 수 없습니다

**【이 섹션의 핵심】 첫 번째 버전은 잠금 해제를 위한 일회성 결제만 유지하며, 복잡한 기능을 수행하지 않으면 출시 속도가 느려집니다. **

더 빨리 온라인에 접속하려면 첫 번째 버전을 건너뛸 수 있습니다.

- 사용자 등록.
- 백엔드 CMS.
- 할인 코드.
- 구독하다.
- 복잡한 데이터베이스.
- 자동 이메일.
- 여러 제품 패키지.

잠금을 해제하려면 먼저 일회성 결제를 한 후 천천히 추가해야 합니다.

> 💡 **왜 이러는 걸까요#  **
> 제품 초기 단계에서 가장 확인해야 할 것은 "테스트를 완료하고 결제할 의향이 있는 사람이 있는가# "이다. 처음에 많은 주변 기능을 수행하는 것보다 먼저 이 메인 라인을 실행하는 것이 더 가치 있습니다.

## Codex의 제품 프로세스 프롬프트

**[이 섹션의 핵심] 이미 해체된 제품 프로세스를 Codex에서 실행할 수 있는 프롬프트 단어로 직접 변환합니다. **

이것을 복사하세요:

```text
일회성 비용으로 보고서를 잠금해제하는 퀴즈 사이트를 만들고 싶습니다.

다음 사용자 경로에 따라 코드를 디자인하십시오.
홈 -> 답변 페이지 -> 무료 소개 보고서 -> 결제 -> 전체 보고서

첫 번째 버전의 경우 로그인, 구독, 할인 코드가 필요하지 않습니다.

디자인을 도와주세요:
1. 프런트 엔드 페이지 상태
2. ReportId 생성 및 저장 방법
3. 결제 세션 데이터 구조
4. 액세스 토큰 잠금 해제 로직
5. 모의결제 테스트 과정

파일 계획을 먼저 출력한 후 최소 버전을 구현하십시오.
```

## 이 장의 완료 기준

**【이 섹션의 핵심】이 장을 완료한 후에는 전체 유료 잠금 해제 프로세스를 중국어로 설명할 수 있어야 합니다. **

완료되면 다음과 같이 명확하게 말할 수 있어야 합니다.

- 사용자가 거치는 페이지.
- 백엔드가 필요한 단계는 무엇입니까?
- 결제가 이루어졌는지 확인하기 위해 프런트 엔드에만 의존할 수 없는 이유는 무엇입니까?
- `reportId`, `payment_session`, `accessToken`는 무엇을 담당하는가?
다음 장에서는 Codex가 실제로 코드를 작성하는 과정을 시작합니다.
