# 06. 복사 가능한 프롬프트 단어 템플릿

![프롬프트 템플릿 장 아트](../../assets/chapters/chapter-06-prompts.webp)
**[이 장의 핵심] 다음은 웹사이트 구축, GitHub 업로드, Zeabur 배포, Paddle 연결 및 오류 문제 해결을 위해 Codex에 직접 게시할 수 있는 프롬프트 단어 모음입니다. **

이 장은 도구 상자입니다. 아래 프롬프트 단어를 Codex에 직접 붙여넣은 다음 괄호 안의 내용을 자신의 프로젝트로 바꿀 수 있습니다.

> 💡 **왜 이러는 걸까요#  **
> 초보자에게 가장 어려운 것은 "무엇을 해야할지 아는 것"이 아니라 "Codex에 어떻게 요청해야 할지 모르는 것"일 때가 많습니다. 템플릿은 표현 비용을 줄이고 요구사항을 더욱 안정적으로 만들 수 있습니다.

## 0. Codex가 먼저 프로젝트를 읽도록 하세요

**[이 섹션의 핵심] 수정하기 전에 Codex가 프로젝트 구조를 이해하도록 하십시오. **

```text
이 프로젝트를 먼저 읽어보시고 성급하게 수정하지 마세요.

나에게 말해주세요:
1. 프론트 엔드 입구는 어디에 있습니까?
2. 백엔드 입구는 어디에 있나요?
3. 결제 구성은 어디에 있나요?
4. 로컬에서 실행하는 방법
5. GitHub에 제출할 수 없는 파일

그런 다음 변경을 위해 제안된 다음 단계를 나열하십시오.
```

## 1. 빈 디렉터리에서 최소 버전 만들기

**[이 섹션의 핵심] 빈 프로젝트에서 시작할 때 먼저 Codex에 최소 실행 가능 버전을 생성하도록 요청하세요. **

```text
현재 디렉터리에 유료 퀴즈 사이트의 사용 가능한 최소 버전을 만드세요.

기술 요구 사항:
- React + Vite 프론트엔드
- Node.js 백엔드
- 모의카드로 먼저 결제
- 실제 패들과 연결되지 않음
- 로그인이 필요하지 않습니다

제품 프로세스:
홈 -> 답변 페이지 -> 무료 소개 보고서 -> 결제 버튼 -> 모의 잠금 해제 -> 전체 보고서

다음을 제공하십시오:
- package.json 스크립트
- 프런트엔드 페이지
- 백엔드 API
- 공개/monetization.json
- .env.지불.예제
- 로컬 작동 지침
```

## 2. 제목 및 결과 페이지 추가

**[이 섹션의 핵심] 프로세스가 완료되면 질문 수 및 결과 페이지가 확장됩니다. **

```text
시험 문제를 [질문 수]개의 질문으로 확장할 수 있도록 도와주세요.

요구사항:
- 각 질문에는 3~5개의 옵션이 있습니다.
- 사용자는 한 번에 하나의 질문만 볼 수 있습니다.
- 진행 프롬프트가 있습니다
- 답변 후 ReportId 생성
- 결과 페이지는 답변을 바탕으로 안정적인 결과를 생성합니다.
- 새로 고친 후에도 현재 보고서를 잃지 마세요

로컬 데이터를 먼저 사용하고 데이터베이스에 연결하지 마십시오.
```

## 3. 무료 소개 보고서 최적화

**【이 섹션의 핵심】무료 페이지는 신뢰를 구축해야 하며 과장된 광고로 작성되어서는 안 됩니다. **

```text
미지급 결과 페이지를 최적화하세요.

스타일:
- 전문적이고 객관적이며 신뢰할 수 있는 분
- 마케팅을 과장하지 마세요.
- “먼저 조금 공개해라”, “고충점을 정확히 짚어라” 같은 말은 하지 마세요.

콘텐츠 구조:
1. 핵심 심리적 원동력
2. 행동 경향과 잠재적인 정체 지점
3. 자기 인식과 내부 및 외부 성과의 조화
4. 완성된 보고서는 분석 방향을 이어갑니다.

제한사항:
- 전체 경력 답변을 표시하지 않습니다.
- 전체 행동 경로를 보여주지 않습니다.
- 보고서 저장 입구 전체를 표시하지 않습니다.
```

## 4. 모의 페이월 추가

**【이 섹션의 핵심】모의 결제를 사용하여 잠금 해제 논리를 먼저 테스트하고, 실제 결제를 받기 위해 서두르지 마세요. **

```text
모의 페이월을 추가해 주세요.

요구사항:
- public/monetization.json이 스위치를 활성화했습니다.
- 활성화=false인 경우 개발에 편리하며 전체 보고서를 직접 볼 수 있습니다.
- 활성화=true일 경우, 결제 없이 무료 소개만 시청할 수 있습니다.
-결제 버튼을 클릭하면 결제 세션이 생성됩니다.
- 모의는 결제 성공 후 자동으로 잠금 해제됩니다.
- 프런트 엔드는 URL 매개변수로 가짜 잠금 해제를 할 수 없습니다.
```

## 5. 먼저 GitHub에 업로드하세요

**[이 섹션의 핵심] 배포하기 전에 Codex에서 GitHub 업로드 보안을 확인하세요. **

```text
이 프로젝트가 GitHub에 업로드하기에 적합한지 확인해주세요.

요구사항:
- .gitignore는 .env, .env.*, *.local, node_modules, dist, 로그, 임시 파일을 무시합니다.
- 프로젝트를 스캔하여 Paddle API 키, 웹훅 비밀 또는 관리자 토큰이 없는지 확인하세요.
- README가 프로젝트의 목적과 로컬에서 실행하는 방법을 설명할 수 있는지 확인하세요.
-GitHub에 처음 업로드할 때 어떤 명령어를 실행해야 하는지 알려주세요.
- 원격 원본이 존재하지 않는 경우 GitHub repo에 연결하는 방법을 알려주세요.
- 비밀이 발견되면 파일 경로를 나열하고 해당 키를 취소하거나 교체하도록 알려주세요.

로컬 키, 실제 주문 데이터 또는 배경 화면 데이터를 Git에 제출하지 마세요.
```

## 6. 그런 다음 Zeabur에 배포합니다.

**[이 섹션의 핵심] GitHub 저장소가 준비되면 Codex에서 Zeabur 배포 조건을 확인하도록 합니다. **

```text
Zeabur에 배포할 수 있도록 프로젝트를 검토하고 조정하시기 바랍니다.

요구사항:
- npm run build는 프런트엔드 파일을 생성할 수 있습니다.
- npm run start는 단일 노드 서비스를 시작할 수 있습니다.
- 서비스 청취 process.env.PORT
- 호스트 사용 가능 0.0.0.0
- 동일한 서비스가 프런트엔드 dist 및 /api를 제공합니다.
- /api/health 추가됨
- .gitignore는 .env, *.local, node_modules, dist, 로그, 임시 파일을 무시합니다.
- API 키를 제출하지 마세요.
- 패들 공급자가 활성화되지 않은 경우 패들 키가 누락되어도 서비스가 중단되지 않아야 합니다.

Zeabur Variables에는 무엇을 채워야 하는지 알려주세요.
```

## 7. 도메인 이름을 확보한 후 Paddle에 연결합니다.

**[이 섹션의 핵심] Zeabur HTTPS 도메인 이름이 준비되면 Paddle에 연결합니다. **

```text
이미 Zeabur HTTPS 도메인 이름이 있고 이제 Paddle에 연결하고 싶습니다.

새 패들 공급자를 추가하세요.

환경 변수:
-PADDLE_ENVIRONMENT
-PADDLE_API_KEY
- PADDLE_CNY_PRICE_ID
-PADDLE_USD_PRICE_ID
- PADDLE_WEBHOOK_SECRET
- PUBLIC_BASE_URL

백엔드 요구 사항:
- POST /api/결제/체크아웃 호출 패들 거래 생성
- custom_data는 reportId 및 Payment_session_id를 작성합니다.
- POST /api/webhooks/paddle 검증 패들 서명
- 거래만 수락하세요. 잠금 해제가 완료되었습니다.
- 실패, 취소, 만료는 잠금 해제되지 않습니다.
- 웹훅 반복 전송은 멱등성이 있어야 합니다.
- 가격 ID, 금액, 통화가 일치하지 않아 잠금 해제할 수 없습니다.
```

## 8. 왜 Zeabur 502인지 확인해보세요

**【이 섹션의 핵심】502를 만나면 위치 확인을 위해 Zeabur 로그를 Codex에 게시하세요. **

```text
Zeabur가 배포된 후 웹사이트를 열면 502가 표시됩니다.

이것은 Zeabur 로그입니다:
[포스트 로그]

확인하세요:
1. package.json 시작 스크립트
2. 서버가 process.env.PORT를 수신하는지 여부
3. 호스트가 0.0.0.0인지 여부
4. 빌드 후 정적 파일 경로가 올바른가요?
5. 환경변수 부족으로 프로세스가 종료되는지 여부

직접 고쳐주세요.
```

## 9. 결제 후 패들이 잠금 해제되지 않는 이유 확인

**【이 섹션의 핵심】결제 후에도 잠금이 해제되지 않으면 Paddle webhook과 Zeabur 로그를 동시에 확인하세요. **

```text
결제 후 패들 페이지가 잠금 해제되지 않습니다.

나는 다음 정보를 가지고 있습니다:
- 패들 거래 ID : [입력]
- 결제 세션 ID: [입력]
- 보고서 ID: [입력]
- Zeabur 로그 : [포스트 로그]
- 패들 웹훅 로그: [포스트 로그]

확인하세요:
1. 웹훅 수신 여부
2. 웹훅 서명이 검증되었나요?
3. event_type이 transaction.completed인지 여부
4. custom_data에 Payment_session_id 및 reportId가 포함되어 있는지 여부
5. 스토어 파일 쓰기 성공 여부
6. 프론트엔드에서 급여를 받을지 여부를 투표합니다.
```

## 10. 온라인 접속 전 보안 감사

**[이 섹션의 핵심] 온라인에 접속하기 전에 비밀, 서명 확인, 권한 및 우회 위험을 중앙에서 확인합니다. **

```text
온라인에 접속하기 전에 보안 감사를 수행하십시오.

핵심 사항:
- 공개파일의 비밀유출 여부
- .env가 git에 의해 추적되는지 여부
- API 키가 백엔드 process.env에만 있는지 여부
- 웹훅의 서명 확인 여부
- 잘못된 서명은 잠금 해제할 수 없습니다.
- 중복된 Webhook은 반복적으로 발급되지 않습니다.
- 결제 없이는 전체 보고서에 액세스할 수 없습니다.
- 동일한 액세스 토큰으로는 다른 사람의 ReportId를 잠금 해제할 수 없습니다.

문제를 나열하고 수정하세요.
```

## 11. 보고서를 제품과 비슷하게 만들기

**【이 섹션의 핵심】기본 링크가 실행된 후 Codex가 보고 경험을 최적화하도록 하세요. **

```text
유료 제품처럼 보이도록 전체 보고서 페이지를 최적화하세요.

요구사항:
- 첫 화면에서 핵심 결론과 레이더를 확인하세요
- 심리적 프로파일링이 주요 판매 포인트입니다.
- 긴 글이 아닌 다방향 짧은 모듈
- 급여 및 채용 시장 설명이 제거되었습니다.
- 성격 특성, 적합한 직업 유형, 개발 경로 및 위험 경계에 중점을 둡니다.
- 대체 직업은 원클릭으로 전환할 수 있지만, 다시 잠글 수는 없습니다.
- 보고서를 저장할 때 레이아웃이 잘리지 않습니다.
```

## 12. Codex를 과하게 사용하지 마세요.

**【이 절의 핵심】작은 변경만 하려는 경우 Codex의 수정 범위를 명확하게 제한해야 합니다. **

Codex가 너무 많이 변경되었다고 생각되면 다음 단락을 사용하십시오.

```text
새로운 기능 추가를 중단해주세요.
이번에는 제가 지적한 문제만 수정하겠습니다.
불필요한 파일을 리팩터링하지 마세요.
시각적 스타일을 변경하지 마십시오.
기존 기능을 제거하지 마세요.
계속하기 전에 어떤 파일을 변경할지 설명해 주세요.
```

## 13. 매번 끝날 때마다 확인이 필요합니다

**【이 섹션의 핵심】 각 수정 후에 Codex는 확인을 실행하고 결과를 설명해야 합니다. **

각 작업이 끝나면 다음을 추가하세요.

```text
완료되면 다음을 실행하세요.
- npm 실행 유형 검사
- npm 실행 빌드

프로젝트에 이러한 명령이 없는 경우 대체 확인 방법을 설명해 주세요.
마지막으로 변경된 사항과 이를 수동으로 테스트하는 방법을 요약해 주세요.
```

## 사용 제안

**【이 섹션의 핵심】한 번에 하나의 템플릿만 붙여넣고 다음 단계로 진행하기 전에 승인이 통과될 때까지 기다립니다. **

초보자를 위한 가장 안정적인 방법은 다음과 같습니다.

1. 한 번에 하나의 프롬프트 단어만 게시하십시오.
2. 코덱스가 수정될 때까지 기다립니다.
3. 달리세요.
4. 화면 상태를 설명하거나 오류를 게시합니다.
5. 다음 단계로 이동합니다.

"완벽한 웹사이트 + 결제 승인 + 배포 + 다국어 + 아트 업그레이드"를 한꺼번에 요구하지 마세요. 그런 식으로 실패하면 어느 단계가 깨졌는지 알기가 어렵습니다.
