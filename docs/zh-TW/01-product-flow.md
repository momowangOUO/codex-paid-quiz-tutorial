# 01. 產品流程怎麼拆

![Product flow chapter art](../../assets/chapters/chapter-01-flow.webp)
**本章重點：寫程式前，先把使用者從進站、作答、看到免費導言、付款到解鎖完整報告的路徑拆清楚。**

你不需要一開始就懂架構。先回答一個問題：使用者會依序看到哪些畫面？

```text
首頁 -> 作答頁 -> 免費導言版報告 -> 付款 -> 完整報告 -> 儲存或回到報告
```

這條路徑越短，越適合第一版。低價一次性報告最重要的是降低阻力，不要一開始就加入會員、折扣碼、複雜後台。

## 每個畫面的任務

| 畫面 | 使用者看到什麼 | 主要任務 | 是否需要後端 |
| --- | --- | --- | --- |
| 首頁 | 測驗價值、開始按鈕 | 讓使用者開始 | 不一定需要 |
| 作答頁 | 題目、選項、進度 | 收集答案 | 通常不需要 |
| 免費導言 | 部分心理與行為分析 | 建立信任 | 需要 reportId |
| 付款頁 | 價格、付款按鈕、等待狀態 | 建立付款 session | 需要 |
| 完整報告 | 雷達、心理側寫、職涯方向、路線 | 交付付費內容 | 需要 access token |

## 免費版應該給到什麼程度

免費版不是故意吊胃口，也不是只放空話。它應該讓使用者相信測驗是有邏輯的。可以提供：

- 核心心理驅動力。
- 行為傾向與潛在卡點。
- 自我認知與外在表現的落差。
- 完整報告會分析哪些面向。

但不要在免費版直接揭露完整職缺清單、完整路線、可儲存報告或所有匹配邏輯。

## 三個重要資料物件

### reportId

`reportId` 是一份測驗結果的編號。作答、付款、解鎖、回到報告頁，都應該對應到同一個 `reportId`。你可以把它想成取餐號碼。

### payment session

`payment_session` 是一次付款嘗試。使用者可能付款失敗、關掉頁面、重試付款，所以付款狀態不能只存在前端。

```json
{
  "sessionId": "pay_xxx",
  "reportId": "rep_xxx",
  "provider": "paddle",
  "status": "pending"
}
```

### access token

`accessToken` 是付款成功後開啟完整報告的鑰匙。不要只因為某個 `reportId` 曾經被付費，就讓所有人都看得到完整報告。

## 給 Codex 的提示詞

```text
我想做一個一次性付費解鎖報告的測驗網站。

使用者路徑：首頁 -> 作答頁 -> 免費導言報告 -> 付款 -> 完整報告。

第一版不要登入、不要訂閱、不要折扣碼。

請幫我設計：
1. 前端頁面狀態
2. reportId 如何產生與保存
3. payment session 資料結構
4. access token 解鎖邏輯
5. mock 付款測試流程

請先輸出檔案計畫，再實作最小版本。
```

## 本章完成標準

- 你能說清楚使用者會經過哪些畫面。
- 你知道哪一步需要後端。
- 你知道為什麼不能靠 `paid=true` 這種網址參數解鎖。
- 你能分清楚 `reportId`、`payment_session`、`accessToken` 的責任。
