# 01. 產品流程怎麼拆

![Product flow chapter art](../../assets/chapters/chapter-01-flow.webp)
**【本章核心】寫程式前先把「使用者會看到哪些頁面、每一步做什麼、哪一步需要後端」拆清楚。 **

開始寫程式之前，你只需要先回答一個問題：

```text
用戶從進站到付費解鎖，會經過哪些畫面？
```

這一章不講架構圖，先把產品拆成 Codex 能理解的小任務。

> 💡 **為什麼要這樣做？ **
> Codex 需要明確的任務邊界。產品流程像一張路線圖：先知道用戶從哪裡進來、在哪裡答題、在哪裡付款、在哪裡看報告，後面寫代碼才不會東補一塊、西補一塊。

## 先畫最短使用者路徑

**【本節核心】先寫出使用者從首頁到完整報告的最短路線。 **

付費測驗網站的最短路徑是：

```text
首頁
  -> 答案頁
  -> 自由導言報告
  -> 付款頁
  -> 完整報告
  -> 儲存或再次開啟報告
```

你可以先不要做登入。低價一次性報告最重要的是減少阻力。

> 💡 **為什麼要這樣做？ **
> 登入、會員、後台、優惠碼都可以以後再加。第一版先讓用戶能完成一次完整購買，就像先確認櫃檯真的能收錢，再裝修更多貨架。

## 每個頁面要做什麼

**【本節核心】每個頁面只負責一個主要任務，避免第一版變得過重。 **

### 首頁

首頁只負責讓使用者開始。

需要有：

- 一句話說明這個測驗幫用戶解決什麼問題。
- 開始按鈕。
- 可選：語言切換、案例入口。

不要一開始就寫「付費解鎖」「馬上購買」。用戶還沒投入時間，太早提錢會降低完成率。

### 答案頁

答題頁只負責讓使用者完成題目。

需要有：

- 目前題號。
- 題目。
- 選項。
- 上一題/下一題。
- 進度提示。
- 圖片或視覺輔助。

新手建議先做 5 題測驗版，流程跑通後再擴充成 48 題。

### 免費導言報告

免費版不是故意吊胃口，也不是空話。它要讓使用者覺得你專業。

可以顯示：

- 核心心理驅力。
- 行為傾向與潛在卡點。
- 自我認知與外在表現差距。
- 完整報告會繼續分析哪些方向。

不要顯示：

- 完整職業答案。
- 完整路徑。
- 詳細行動計劃。
- 可儲存的完整報告。

### 付費牆

付費牆只負責讓用戶付款。

需要有：

- 當前價格。
- 一個清楚的付款按鈕。
- 付款後自動解鎖說明。
- 付款失敗或等待中的狀態。

不要同時塞太多付款方式按鈕。後端可以根據地區推薦一個入口。

### 完整報告

完整報告要讓使用者覺得「這不是隨便產生一段文字」。

可以包含：

- 職業雷達。
- 心理側寫。
- 適合的職業類型。
- 多條發展路線。
- 風險邊界。
- 備選方向。
- 儲存報告。

## 用表格交給 Codex

**【本節核心】把頁面、使用者動作、後端參與方式整理成表格，再交給 Codex。 **

把你的產品流程整理成這張表，再貼給 Codex：

| 頁面 | 使用者看到什麼 | 使用者能做什麼 | 後端要不要參與 |
| --- | --- | --- | --- |
| 首頁 | 產品說明、開始按鈕 | 開始測驗 | 不需要 |
| 答題頁 | 題目與選項 | 作答、下一題 | 不需要，除非要即時儲存 |
| 免費報告 | 部分分析、解鎖按鈕 | 點擊付款 | 需要建立 payment session |
| Paddle checkout | 付款表單 | 付款 | Paddle 處理 |
| 完整報告 | 全部分析 | 檢視、儲存 | 需要驗證 access token |

## reportId 是什麼

**【本節核心】`reportId` 是某一份測驗報告的編號。 **

`reportId` 是一份報告的編號。

使用者答完題後，前端產生或後端產生一個 `reportId`，後續所有動作都圍繞著它：

```text
這份答案 -> reportId
這筆訂單 -> reportId
這次解鎖 -> reportId
這份完整報告 -> reportId
```

沒有 `reportId`，付款平台告訴你“有人付錢了”，你也不知道該解鎖哪份報告。

> 💡 **為什麼要這樣做？ **
> `reportId` 像是取餐號碼。用戶點了餐、付了錢、回來取餐，都要靠同一個號碼對應同一份內容。

## payment session 是什麼

**【本節核心】`payment_session` 是某一次付款嘗試的記錄。 **

`payment_session` 是一次付款嘗試。

一個使用者可能：

- 點選付款但關閉頁面。
- 付款失敗。
- 重試付款。
- 付款成功但前端沒跳回來。

所以不要只靠前端狀態。後端要儲存：```json
{
  "sessionId": "pay_xxx",
  "reportId": "rep_xxx",
  "provider": "paddle",
  "providerOrderId": "txn_xxx",
  "status": "pending"
}
```

付款成功後改成：```json
{
  "status": "paid",
  "paidAt": "2026-05-28T00:00:00.000Z"
}
```

> 💡 **為什麼要這樣做？ **
> 一份報告可能會有多次付款嘗試。用戶可能第一次關掉付款頁，第二次才成功。 `payment_session` 可以把這些嘗試分開記錄，避免狀態混亂。

## access token 是什麼

**【本節核心】`accessToken` 是付款成功後打開完整報告的鑰匙。 **

`accessToken` 是完整報告的鑰匙。

付款成功後，後端給這份報告一個不可猜測的 token。使用者下次回來時，前端帶著 token 問後端：

```text
這份 token 有沒有權限看 reportId 這份報告？
```

後端說可以，才顯示完整報告。

> 💡 **為什麼要這樣做？ **
> 不應該只靠「這個 reportId 已經有人付過錢」來顯示完整報告，否則別人刷到同一個 reportId 可能也能看。 `accessToken` 像專屬鑰匙，只有拿到鑰匙的人才能打開。

## 第一版可以先不做什麼

**【本節核心】第一版只保留一次付費解鎖，先不做會拖慢上線的複雜功能。 **

為了更快上線，第一版可以先不做：

- 用戶註冊。
- 後台 CMS。
- 優惠碼。
- 訂閱。
- 複雜資料庫。
- 自動郵件。
- 多個產品套餐。

你先跑通一次性付款解鎖，再慢慢加。

> 💡 **為什麼要這樣做？ **
> 產品早期最需要驗證的是「有沒有人願意完成測驗並付款」。先把這條主線跑通，比一開始做很多周邊功能更有價值。

## 給 Codex 的產品流程提示詞

**【本節核心】把已經拆好的產品流程直接變成 Codex 可以執行的提示詞。 **

複製這段：

```text
我想做一個一次性付費解鎖報告的測驗網站。

請依照這個使用者路徑設計程式碼：
首頁 -> 答案頁 -> 免費導言報告 -> 付款 -> 完整報告

第一版不要登入、不要訂閱、不要優惠碼。

請幫我設計：
1. 前端頁面狀態
2. reportId 如何產生與儲存
3. payment session 資料結構
4. access token 解鎖邏輯
5. mock 支付測試流程

請先輸出文件計劃，再實現最小版本。
```
