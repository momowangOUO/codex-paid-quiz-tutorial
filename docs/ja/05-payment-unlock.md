# 05. ドメイン名を取得したら、Paddle 支払いを受け入れ、自動的にロックを解除します。

![パドル決済アンロックチャプターアート](../../assets/chapters/chapter-05-paddle.webp)
この章は、前の章を完了し、HTTPS ドメイン名を取得していることを前提としています。次に例を示します。

```text
https://your-project.zeabur.app
```

**【この章の核心】Zeabur ドメイン名を使用して Paddle 設定を完了し、バックエンドが Paddle Webhook を通じてレポートのロックを自動的に解除できるようにします。 **

この章はコードから始まるのではなく、Paddle がバックグラウンドで必要とするものを最初に完成させます。

> 💡 **なぜこれを行うのですか#  **
> パドルはボタンを与えるだけではありません。アカウント、製品、ドメイン、支払いページ、通知アドレスがチェックされます。バックグラウンドデータが完成していない場合、正しくコードを記述しても`checkout not enabled`などのエラーが発生する場合があります。

### ステップ 1: まず、リンク全体で Paddle が何を行うかを理解します。

**【このステップの核心】Paddle は集金と支払い結果の通知を担当し、Web サイトは注文の作成とレポートのロック解除を担当します。 **

完全なプロセスは次のとおりです。

```text
ユーザーがクリックしてロックを解除する
  -> ウェブサイトのバックエンドが支払いセッションを作成します
  -> バックエンドが Paddle にチェックアウトの作成をリクエストします。
  -> ユーザーは Paddle ページで支払います
  -> Paddle は Webhook を使用してバックエンドに通知します
  -> バックエンドは支払いが有効であることを確認します
  -> バックエンドのロック解除に対応するレポート ID
```Web サイトでは次の 3 つのことを行う必要があります。

1. チェックアウトを作成します。
2. Webhook を受信して​​確認します。
3. 支払い確認後にアクセス権が発行されます。

パドルは次の 3 つのことを行います。

1. 決済ページを表示します。
2. クレジット カード、PayPal、または一部の地域で利用できる現地の支払い方法を処理します。
3. 支払い結果をバックエンドに送り返します。

> 💡 **なぜこれを行うのですか#  **
> ユーザーの支払いをフロントエンド Web ページの判断に任せることはできません。フロントエンドは店舗の陳列エリアに似ており、バックエンドはレジ システムに似ており、Paddle はサードパーティのチェックアウト カウンターに似ています。チェックアウト デスクがバックエンドに「お金が確認された」ことを通知した場合にのみ、バックエンドはドアを開けてレポートを配信する必要があります。

### ステップ 2: Paddle のオンボーディングを完了する

**【このステップの核心】まず、Paddle アカウントをチェックアウトを作成できるようにします。 **

Paddle バックエンドに入り、必要に応じて次のページに入力します。

1. アカウントまたは会社情報。
2. 販売する製品の種類。
3. 製品の説明。
4. 年収の範囲。
5. 支払い方法。
6. Web サイトのドメイン名。
7. Paddle の許容使用ポリシーに準拠します。

製品説明は、次のように控えめかつ明確に書くことができます。

```text
当社では、1 回限りのデジタルキャリア評価レポートを販売しています。
ユーザーはクイズに回答すると、パーソナライズされたオンライン レポートを受け取ります。
この製品はデジタル コンテンツへのアクセスであり、雇用斡旋、経済的アドバイス、医療上のアドバイス、またはキャリアの成果の保証ではありません。
```

パドルが表示される場合:

```text
このアカウントではチェックアウトがまだ有効になっていません
```

優先順位のチェック:

1. オンボーディングが完了しているかどうか。
2. ウェブサイトの承認は完了していますか?
3. デフォルトの支払いリンクが設定されているかどうか。
4. 製品と価格が存在するかどうか。
5. アカウントはまだ Paddle のレビューを待っていますか?
> 💡 **なぜこれを行うのですか#  **
> このステップは、レジを開くための販売者のレビューに似ています。 Paddle は、あなたが何を販売しているか、ユーザーが何を購入しているか、そしてそれがプラットフォームのポリシーに準拠しているかどうかを知る必要があります。それは単なる技術的な API ではありません。

### ステップ 3: Web サイト認証を送信する

**[このステップの核心] 前の章で取得した Zeabur ドメイン名を Paddle に入力し、これがあなたの販売 Web サイトであることを Paddle に確認させます。 **

Paddle の Web サイト承認またはドメイン検証ページに次の情報を入力します。

```text
https://your-zeabur-ドメイン名
```Paddle に価格ページが必要な場合は、次のように入力します。

```text
https://ドメイン/価格設定
```Paddle で利用規約、プライバシー、返金が必要な場合は、それぞれ次のように入力します。

```text
https://あなたのドメイン/用語
https://あなたのドメイン/プライバシー
https://あなたのドメイン/払い戻し
```

これらの URL は直接開くことができる必要があり、Web サイトのトップページに入力するだけではいけないことに注意してください。

![Paddle ウェブサイトの確認手順](../../assets/diagrams/04-paddle-domain.svg)

> 💡 **なぜこれを行うのですか#  **
> Paddle はユーザーの視点から Web サイトを確認する必要があります。価格はどこにあるのか、ルールはどこにあるのか、プライバシーに関する指示はどこにあるのか、返金の指示はどこにあるのかなどです。完全なパスを含む URL は、単なるホームページよりも簡単に渡すことができます。

### ステップ 4: デフォルトの支払いリンクを設定する

**[このステップの核心] Tell Paddle: 今後チェックアウトを作成するときに、支払いページにどの検証済みドメイン名を使用する必要があるか。 **

デフォルトの支払いリンク 以下を入力することをお勧めします。

```text
https://your-zeabur-domain/
```

ここでよくある誤解:

1. ユーザーに投稿したい商品リンクではありません。
2. これは Webhook URL ではありません。
3. 特定のレポート ID の結果ページではありません。
4. これは、チェックアウトを作成するときに Paddle によって使用されるアカウントレベルの支払いドメイン名です。

デフォルトの支払いリンクが設定されていない場合、API キーが正しくてもバックエンドでトランザクション チェックアウトを作成できない可能性があります。

> 💡 **なぜこれを行うのですか#  **
> デフォルトの支払いリンクは、「支払いシステムがデフォルトで使用するストアアドレス」と考えることができます。このアドレスがないと、Paddle はどの承認済み Web サイトで支払いページをホストすべきかわかりません。

### ステップ 5: 1 回限りの製品を作成する

**【このステップの核心】Paddle で販売したいデジタル レポート製品を作成します。 **

以下を入力することをお勧めします。

|フィールド |推奨される書き込み |
| --- | --- |
|製品名 | AI キャリア アクション レポート、またはレポート名 |
|説明 |パーソナライズされたデジタルキャリア評価レポートに 1 回限りアクセスできます。 |
|製品タイプ |デジタル製品 |
|税金のカテゴリー |デジタル グッズ、電子書籍、または現在 Paddle アカウントに許可されている最も近いカテゴリ |

製品が実際に月額料金を請求する場合を除き、サブスクリプションや長期メンバーシップとして記述しないでください。

> 💡 **なぜこれを行うのですか#  **
> 製品は「あなたが販売するもの」です。 1 回限りのレポートの場合、製品はクラス、キャリア サービス、または人間によるコンサルティングへのコミットメントではなく、デジタル コンテンツへの 1 回限りのアクセスである必要があります。

### ステップ 6: 2 つのワンタイム価格を作成する

**【このステップの核心】同一商品に対して国内と海外の2つのワンタイム価格を設定します。 **

最初にビルドすることをお勧めします。

|目的 |通貨と価格 |説明 |
| --- | --- | --- |
|国内価格 | 9.90元 |中国地域または中国人ユーザー向け |
|海外価格 | 1.99ドル |海外のクレジットカード/PayPalユーザー向け |

価格タイプの選択:

```text
一度
```

サブスクリプションは選択しないでください。

作成後、2 つの価格 ID をコピーします。```bash
PADDLE_CNY_PRICE_ID=pri_xxx
PADDLE_USD_PRICE_ID=pri_xxx
```

!【パドル商品と価格説明】(../../assets/diagrams/05-paddle-product-price.svg)

> 💡 **なぜこれを行うのですか#  **
> Product は製品そのものであり、Price はこの製品の特定の販売価格です。製品には、人民元価格や米ドル価格など、複数の価格を設定できます。バックエンドがチェックアウトを作成するとき、価格 ID を使用して、今回いくら請求するかを Paddle に伝えます。

### ステップ 7: API キーを作成し、Zeabur 変数に入れます。

**【このステップの核心】 API キーはバックエンドでのみ使用され、フロントエンドのパブリック ファイルに含めてはなりません。 **

Paddle Developer ツールで API キーを作成します。

次に、Zeabur の変数を入力し、次のように入力します。```bash
PADDLE_ENVIRONMENT=sandbox
PADDLE_API_KEY=你的_sandbox_api_key
PADDLE_CNY_PRICE_ID=pri_xxx
PADDLE_USD_PRICE_ID=pri_xxx
```

注意してください:

1. サンドボックス キーはサンドボックスの価格と一致します。
2. ライブキーはライブ価格とペアになります。
3. 混ぜないでください。
4. `public/monetization.json` には API キーを書き込まないでください。
5. API キーをフロントエンド `.tsx`、`.js`、および `.html` に書き込まないでください。

正しい概念は次のとおりです。

```text
ブラウザのフロントエンド: 「支払いたい」ことのみを認識
バックエンド: API キーを Paddle に渡してチェックアウトを作成します
パドル: 支払いページの URL に戻る
```

> 💡 **なぜこれを行うのですか#  **
> API キーはチェックアウト バックエンド キーのようなものです。ユーザーのブラウザは公共の場所であり、フロントエンドに置かれたものはすべて表示される可能性があります。キーは、バックエンドまたはデプロイメント プラットフォームの環境変数にのみ配置できます。

### ステップ 8: Webhook を設定する

**【このステップの核心】支払い完了後にウェブサイトに通知するアドレスを Paddle に知らせます。 **

パドル通知の宛先を入力します:

```text
https://your-zeabur-domain/api/webhooks/paddle
```

少なくとも次のイベントを選択してください:

```text
取引完了しました
トランザクション.支払い_失敗
取引がキャンセルされました
トランザクション.past_due
```

次に、Webhook シークレットをコピーし、Zeabur 変数に入力します。```bash
PADDLE_WEBHOOK_SECRET=你的_webhook_secret
PADDLE_ALLOW_UNSIGNED_WEBHOOKS=false
```

![パドル Webhook 信号](../../assets/diagrams/06-paddle-webhook.svg)

> 💡 **なぜこれを行うのですか#  **
> Webhook は、Paddle がバックエンドに「このトランザクションは完了しました」という呼び出しを積極的に行うようなものです。 Webhook シークレットは、双方が合意したパスワードのようなものです。秘密コードがなければ、誰かが電話をかけ、支払いをしたと偽ることもできます。

### ステップ 9: バックエンドにパドルチェックアウトを作成させます

**[このステップの核心] ユーザーが支払いボタンをクリックすると、フロントエンドはバックエンドのみを要求し、Paddle API キーに直接接続しません。 **

フロントエンドリクエスト:```http
POST /api/payments/checkout
Content-Type: application/json

{
  "reportId": "rep_xxx",
  "region": "domestic"
}
```

バックエンドは次のことを行う必要があります。

1. ローカル支払いセッションを作成します。
2. 地域に応じて、`PADDLE_CNY_PRICE_ID` または `PADDLE_USD_PRICE_ID` を選択します。
3. Paddle 作成トランザクション API を呼び出します。
4. `reportId` を `custom_data` に入れます。
5. `payment_session_id` を `custom_data` に入れます。
6. Paddle トランザクション ID を保存します。
7. Paddle チェックアウト URL をフロントエンドに返します。

コーデックスに関するヒント:

```text
すでに Zeabur HTTPS ドメイン名を持っているので、Paddle に接続したいと考えています。

新しい Paddle プロバイダーを追加してください。

要件:
1. テストを容易にするために、モックプロバイダーを保持します。
2. POST /api/payments/checkout は、Paddle 作成トランザクションを呼び出します。
3. 国内では PADDLE_CNY_PRICE_ID を使用し、海外では PADDLE_USD_PRICE_ID を使用します。
4. トランザクションのカスタムデータには、reportId とpayment_session_id が含まれている必要があります。
5. すべてのシークレットは process.env からのみ読み取ることができます。
6. public/monetization.json にはシークレットを含めることはできません。
```

> 💡 **なぜこれを行うのですか#  **
> `custom_data` は、Paddle の注文に記入した「付箋」です。 Webhook が戻ってくると、バックエンドはこのメモに基づいて、この支払いがどのレポートと支払いセッションに対応しているかを認識します。

### ステップ 10: Webhook のみでレポートのロックを解除できるようにする

**【このステップの核心】 ユーザーがページに戻った、URL にさらに多くのパラメーターがある、またはフロントエンド表示が成功したからといって、直接ロックを解除しないでください。 **

Paddle はバックエンドに次のように通知します。

```text
POST /api/webhooks/paddle
```

バックエンドは次のチェックを行う必要があります。

1. `Paddle-Signature` を生のボディで検証します。
2. `transaction.completed` のみ受け付けます。
3. `custom_data.payment_session_id` を確認します。
4. `custom_data.report_id` を確認します。
5. 価格 ID を確認します。
6. 金額を確認します。
7. 通貨を確認します。
8. 繰り返される Webhook は冪等である必要があります。
9. すべてのチェックに合格した後にのみ、`accessToken` を書き込みます。

コーデックスに関するヒント:

```text
POST /api/webhooks/paddle を実装してください。

要件:
1. パドル署名を検証するには生の本文を使用する必要があります。
2.transaction.completed ロック解除のみが受け入れられます。
3.transaction.payment_failed/transaction.canceled/transaction.past_due はロックが解除されていません。
4.custom_data の reportId とpayment_session_id はローカル セッションと一致する必要があります。
5. 価格ID、金額、通貨が一致しない場合、ロックを解除できません。
6. 繰り返し Webhook 権限を繰り返し発行することはできません。
7. トラブルシューティングを容易にするために、エラーはすべてpayment_events に書き込まれる必要があります。
```

> 💡 **なぜこれを行うのですか#  **
> ユーザーの支払いページが Web サイトに戻ります。これはブラウザが戻ったことを意味するだけで、入金が確認されたことを意味するものではありません。本当に信頼できる信号は、Paddle サーバーから送信される署名検証済みの Webhook です。

### ステップ 11: 決まった順序でサンドボックスをテストする

**[このステップの核心] まずサンドボックスを使用して、リンク全体が通過できることを証明してから、ライブに切り替えます。 **

次に、次の順序でテストします。

1. Zeabur 環境変数のサンドボックス API キーを入力します。
2. Zeabur 環境変数にサンドボックスの価格 ID を入力します。
3. Zeabur 環境変数にサンドボックス Webhook シークレットを入力します。
4. 再展開します。
5. オンライン ドメイン名を開きます。
6. クイズに答えます。
7. 「支払う」をクリックします。
8. Paddle サンドボックスのチェックアウトにジャンプします。
9. Paddle が提供するテスト カードで支払います。
10. パドル通知ログを開きます。
11. Zeabur ログを開きます。
12. Webhook が正常に返されることを確認します。
13. レポートページに戻り、自動ロック解除を確認します。

> 💡 **なぜこれを行うのですか#  **
> サンドボックスとは、決済プラットフォームが提供するテスト環境です。実際にお金を徴収することなく、API、Webhook、ロック解除ロジックが正しいかどうかを確認できます。

### ステップ 12: 一般的なエラーのトラブルシューティング

**【このステップの核心】エラーが表示された場合は、まずそれがアカウント設定、環境変数、コード、または Webhook に問題があるかどうかを判断します。 **

#### チェックアウトはまだ有効になっていません

優先順位のチェック:

1. Paddle のオンボーディングが完了しているかどうか。
2. Web サイトの検証に合格したかどうか。
3. デフォルトの支払いリンクが設定されているかどうか。
4. 製品と価格が確立されているかどうか。
5. アカウントがまだ Paddle によって審査中かどうか。

#### 認証ヘッダーの形式が正しくありません

環境変数にはキー自体のみが含まれます。```bash
PADDLE_API_KEY=pdl_sdbx_xxx
```

リクエストヘッダーは次のとおりです。

```text
権限: ベアラー pdl_sdbx_xxx
```

環境変数には書き込まないでください。```bash
PADDLE_API_KEY=Bearer pdl_sdbx_xxx
```

#### 支払い後にロックが解除されない

順番に確認してください:

1. Paddle 通知ログは Webhook を送信しますか?
2. Zeabur ログはリクエストを受け取りましたか?
3. Webhook URL が `/api/webhooks/paddle` かどうか。
4. Webhook シークレットに一貫性があるかどうか。
5. イベントは`transaction.completed`ですか?
6. `custom_data` には `payment_session_id` と `report_id` はありますか。
7. `/data/payment-store.json` が正常に書き込まれたかどうか。

> 💡 **なぜこれを行うのですか#  **
> 支払いの失敗も同じ理由によるものではない可能性があります。質問を「Paddle は通知を送信しましたか、Zeabur はそれを受信しましたか、バックエンドは検証に合格しましたか、データは書き込まれましたか」に分割することで、どのセクションがスタックしているかをすぐに特定できます。

### ステップ 13: ライブに切り替える前に最終確認を行う

**【このステップの核心】サンドボックスの実行後、Paddle のライブデータを置き換えます。 **

ライブに切り替える前に確認してください:

1. パドルライブオンボーディングに合格しました。
2. ライブ Web サイトの承認が通過しました。
3. ライブデフォルトの支払いリンクが設定されています。
4. ライブプロダクトが作成されました。
5. ライブ一回限りの価格が設定されました。
6. Zeabur 変数はライブ API キーに置き換えられました。
7. Zeabur 変数はライブ価格 ID に置き換えられました。
8. Zeabur 変数はライブ Webhook シークレットに置き換えられました。
9.`PADDLE_ENVIRONMENT=live`。
10. テスト入口、0元ロック解除、模擬ボタンはすべて閉じられています。

> 💡 **なぜこれを行うのですか#  **
> サンドボックスとライブは別の世界です。サンドボックス キーは実際のお金を受け入れることができないため、ランダム テストにはライブ キーを使用しないでください。切り替えるときは、キー、価格 ID、Webhook シークレットが混在しないように、セットで置き換えてください。

### この章の完了基準

**[この章の核心] ユーザーが実際に支払ったことを証明できなければなりません。レポートはバックエンドによって自動的にロック解除されます。 **

完了後、項目ごとに確認してください。

1. ユーザーが支払いボタンをクリックして、Paddle チェックアウトを開きます。
2. Paddle サンドボックスの支払い後、Webhook は Zeabur バックエンドに戻ります。
3. バックエンドは、`transaction.completed` の後にのみロックが解除されます。
4. 間違った署名ではロックが解除されません。
5. 金額を間違えてもロックは解除されません。
6. 間違った価格 ID ではロックが解除されません。
7. 重複した Webhook は繰り返し発行されません。
8. ユーザーは、レポート ページを更新した後も、ロック解除されたコンテンツを表示できます。
9. ブラウザを変更した場合、またはアクセス トークンがない場合、他の人の完全なレポートを表示することはできません。

これらがすべて確立されると、パドル アクセスは真に成功します。
