#06. コピー可能なプロンプト Word テンプレート

![プロンプト テンプレートの章アート](../../assets/chapters/chapter-06-prompts.webp)
**[この章の核心] 以下は、Web サイトの構築、GitHub へのアップロード、Zeabur のデプロイ、Paddle への接続、およびエラーのトラブルシューティングのために Codex に直接投稿できるプロンプト ワードのコレクションです。 **

この章はツールボックスです。以下のプロンプトの単語を Codex に直接貼り付け、括弧内の内容を独自のプロジェクトに置き換えることができます。

> 💡 **なぜこれを行うのですか#  **
> 初心者にとって最も難しいのは、多くの場合、「何をすればよいかわからない」ことではなく、「Codex にそれを依頼する方法がわからない」ことです。テンプレートを使用すると、式のコストを削減し、要件をより安定させることができます。

## 0. 最初に Codex にプロジェクトを読み取らせます

**[このセクションの核心] 変更を加える前に、Codex にプロジェクトの構造を理解させてください。 **

```text
まずこのプロジェクトを読んで、急いで変更しないでください。

教えてください:
1. 正面玄関はどこですか?
2. バックエンドの入り口はどこですか?
3. 支払い設定はどこにありますか?
4. ローカルで実行する方法
5. GitHub に送信できないファイル

次に、変更に向けて提案する次のステップをリストします。
```

## 1. 空のディレクトリから最小バージョンを作成します。

**[このセクションの核心] 空のプロジェクトから開始する場合は、まず Codex に実行可能な最小バージョンを作成するように依頼します。 **

```text
有料クイズ サイトの使用可能な最小バージョンを現在のディレクトリに作成してください。

技術的要件:
- React + Vite フロントエンド
- Node.js バックエンド
- 最初にモックで支払います
- 実際のパドルに接続されていません
- ログインは必要ありません

製品プロセス:
ホーム -> 回答ページ -> 無料導入レポート -> 支払いボタン -> 模擬ロック解除 -> 完全なレポート

以下を提供してください:
- package.json スクリプト
- フロントエンドページ
- バックエンド API
- public/monetization.json
- .env.payment.example
- ローカル操作指示
```

## 2. タイトルと結果ページを追加する

**[このセクションの核心] プロセスが完了すると、質問数と結果ページが拡張されます。 **

```text
テスト問題を [質問数] 個の質問に拡張するのにご協力ください。

要件:
- 各質問には 3 ～ 5 つの選択肢があります
- ユーザーは一度に 1 つの質問のみを参照できます
- 進行状況を示すプロンプトがあります
- 回答後にreportIdを生成します
- 結果ページでは、回答に基づいて安定した結果が生成されます
- 更新後に現在のレポートが失われないようにする

最初にローカル データを使用し、データベースには接続しません。
```

## 3. 無料の紹介レポートを最適化する

**【このセクションの核心】無料のページは信頼を築く必要があり、誇張した広告として書かれるべきではありません。 **

```text
未払いの結果ページを最適化してください。

スタイル:
- プロフェッショナル、客観的、信頼できる
- マーケティングを誇張しないでください
- 「最初に少し明らかにする」とか「問題点を正確に攻撃する」などのことは言わないでください。

コンテンツ構造:
1. 核となる心理的原動力
2. 行動傾向と潜在的な行き詰まり点
3. 自己認識と内部および外部のパフォーマンスの調和
4. 完全なレポートは分析の方向性を継続します

制限事項:
- キャリアに関する完全な回答は表示されません
- 行動の完全なルートを示していない
- レポート全体の保存入り口を表示しない
```

## 4. モックペイウォールを追加する

**【このセクションの核心】最初に模擬支払いを使用してロック解除ロジックをテストし、実際の支払いを急いで受け取らないでください。 **

```text
模擬ペイウォールを追加してください。

要件:
- public/monetization.json でスイッチが有効になりました
- Enabled=false の場合、開発に便利で、完全なレポートを直接表示できます。
- Enabled=true の場合、料金を支払わずに無料の紹介のみを視聴できます。
- 支払いボタンをクリックして支払いセッションを作成します
- 支払いが成功すると、モックは自動的にロック解除されます
- フロントエンドは、URL パラメーターによって疑似ロック解除できません。
```

## 5. まず GitHub にアップロードします

**【このセクションの核心】 デプロイの前に、Codex で GitHub アップロードのセキュリティを確認してください。 **

```text
このプロジェクトが GitHub へのアップロードに適しているかどうかを確認してください。

要件:
- .gitignore は .env、.env.*、*.local、node_modules、dist、ログ、一時ファイルを無視します
- プロジェクトをスキャンして、Paddle API キー、Webhook シークレット、または管理者トークンがないことを確認します。
- README でプロジェクトの目的とローカルでの実行方法が説明されていることを確認します。
-初めてGitHubにアップロードするときに実行するコマンドを教えてください
- リモートオリジンが存在しない場合、GitHub リポジトリに接続する方法を教えてください
- シークレットが見つかった場合は、ファイル パスをリストし、対応するキーを取り消すか置き換えるよう通知してください。

ローカルキー、実際の注文データ、またはバックグラウンド画面データを Git に送信しないでください。
```

## 6. 次に Zeabur にデプロイします

**[このセクションの核心] GitHub リポジトリの準備ができたら、Codex で Zeabur のデプロイ条件を確認します。 **

```text
Zeabur にデプロイできるようにプロジェクトを確認して調整してください。

要件:
- npm run build はフロントエンド ファイルを生成できます
- npm run start は単一ノードのサービスを開始できます
- サービスリスニングプロセス.env.PORT
- 利用可能なホスト 0.0.0.0
- 同じサービスがフロントエンド dist と /api を提供します
- /api/health を追加しました
- .gitignore は .env、*.local、node_modules、dist、ログ、一時ファイルを無視します
- API キーを送信しないでください
- パドルプロバイダーが有効になっていない場合、パドルキーの欠落によってサービスがクラッシュすることはありません。

Zeabur 変数に何を入力すればよいか教えてください。
```

## 7. ドメイン名を取得したら Paddle に接続します

**[このセクションの核心] Zeabur HTTPS ドメイン名の準備ができたら、Paddle に接続します。 **

```text
すでに Zeabur HTTPS ドメイン名を持っているので、Paddle に接続したいと考えています。

新しい Paddle プロバイダーを追加してください。

環境変数:
-PADDLE_ENVIRONMENT
-PADDLE_API_KEY
- PADDLE_CNY_PRICE_ID
-PADDLE_USD_PRICE_ID
- PADDLE_WEBHOOK_SECRET
- PUBLIC_BASE_URL

バックエンドの要件:
- POST /api/payments/checkout 呼び出し Paddle トランザクション作成
-custom_data は、reportId とpayment_session_id を書き込みます
- POST /api/webhooks/paddle 検証 パドル署名
- トランザクションのみを受け入れます。ロック解除が完了しました
- 失敗、キャンセル、期限切れではロックが解除されません
- Webhook の繰り返し送信は冪等である必要があります
- 価格ID、金額、通貨が一致しないため、ロックを解除できません
```

## 8. Zeabur 502 を使用する理由を確認してください

**【このセクションの核心】 502 に遭遇した場合は、測位のために Zeabur のログを Codex に投稿します。 **

```text
Zeabur の展開後、Web サイトを開くと 502 が表示されます。

これは Zeabur のログです。
【投稿ログ】

ご確認ください:
1. package.json 起動スクリプト
2. サーバーが process.env.PORT をリッスンするかどうか
3. ホストが 0.0.0.0 かどうか
4. ビルド後の静的ファイルのパスは正しいですか?
5. 環境変数の不足によりプロセスが終了するかどうか

直接修正してください。
```

## 9. 支払い後にパドルのロックが解除されない理由を確認してください

**【このセクションの核心】 支払い後にロックが解除されない場合は、Paddle Webhook と Zeabur のログを同時に確認してください。 **

```text
支払い後もパドルページのロックが解除されません。

こんな情報があります:
- パドルトランザクション ID: [記入]
- 支払いセッションID: [記入]
- レポートID: [記入]
- ゼアブルログ：[投稿ログ]
- パドル Webhook ログ: [ポストログ]

ご確認ください:
1.Webhookを受信したかどうか
2. Webhook の署名は検証されていますか?
3.event_typeがtransaction.completedかどうか
4.custom_data にpayment_session_id と reportId が含まれるかどうか
5. ストアファイルが正常に書き込まれたかどうか
6. フロントエンドは支払いを受けるかどうかをポーリングします
```

## 10. オンラインにする前のセキュリティ監査

**[このセクションの核心] オンラインにする前にシークレット、署名検証、権限を一元的にチェックし、リスクを回避します。 **

```text
オンラインにする前にセキュリティ監査を行ってください。

重要なポイント:
- 公開ファイルから機密が漏洩していないか
- .env が git によって追跡されるかどうか
- API キーがバックエンド process.env にのみ存在するかどうか
- Webhook が署名を検証するかどうか
- 間違った署名ではロックを解除できません
- 重複した Webhook が繰り返し発行されない
- 料金を支払わないと完全なレポートにアクセスできません
- 同じアクセス トークンで他の人のレポート ID のロックを解除することはできません

問題をリストアップして修正してください。
```

## 11. レポートをより製品らしくする

**【このセクションの核心】基本的なリンクが実行されたら、Codex にレポート エクスペリエンスを最適化させます。 **

```text
完全なレポート ページを最適化して、有料製品のように見えるようにしてください。

要件:
- 最初の画面で核となる結論とレーダーを確認します
- 心理プロファイリングが主なセールスポイントです
- 長い記事ではなく、多方向の短いモジュール
- 給与と雇用市場の説明を削除
- 性格特性、適切なキャリアタイプ、成長ルート、リスク境界に焦点を当てる
- 代替職業はワンクリックで切り替えることができますが、再ロックすることはできません。
- レポートを保存するときにレイアウトが切り取られません。
```

## 12. コーデックスをやりすぎないでください

**【このセクションの核心】小さな変更だけをしたい場合は、Codex の変更範囲を明確に制限する必要があります。 **

コーデックスがあまりにも変更されていると感じる場合は、次の段落を使用してください。

```text
新しい機能の追加はやめてください。
今回は私が指摘した問題のみを修正します。
無関係なファイルをリファクタリングしないでください。
ビジュアルスタイルを変更しないでください。
既存の機能を削除しないでください。
続行する前に、どのファイルを変更するのか説明してください。
```

## 13. 毎回の終了時に検証を要求する

**【このセクションの核心】Codex は、修正を行うたびにチェックを実行し、結果を説明する必要があります。 **

各タスクの最後に次を追加します。

```text
完了したら、次を実行してください。
- npm タイプチェックを実行する
- npm ビルドを実行する

プロジェクトにこれらのコマンドがない場合は、代替の検証方法を説明してください。
最後に、何が変更されたのか、どのように手動でテストする必要があるのか​​をまとめてください。
```

## 使用上の提案

**【このセクションの核心】 テンプレートは一度に 1 つだけ貼り付けて、承認が通過するまで待ってから次のステップに進みます。 **

初心者にとって最も安定した方法は次のとおりです。

1. プロンプトワードは一度に 1 つだけ投稿します。
2. コーデックスが変更されるまで待ちます。
3. 走ります。
4. 画面のステータスまたは投稿エラーを説明します。
5. 次のステップに進みます。

「ウェブサイトの完成 + 支払いの受け入れ + 導入 + 多言語 + アートのアップグレード」を一度に要求しないでください。このように失敗すると、どのステップが壊れているのかを知るのは困難です。
