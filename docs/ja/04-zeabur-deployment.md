# 04. Zeabur にデプロイして検証可能なドメイン名を取得する

!【ゼアブル展開章アート】(../../assets/chapters/chapter-04-zeabur.webp)
この章は、前の章を完了し、プロジェクトを GitHub にアップロードしていることを前提としています。次に、GitHub リポジトリを Zeabur にデプロイします。

**[この章の核心] まず、Web サイトにパブリックにアクセス可能な HTTPS ドメイン名を設定し、このドメイン名を Web サイトの検証、デフォルトの支払いリンク、Webhook に Paddle に使用します。 **

推奨される順序は次のとおりです。

```text
ローカルのモックプロセスがスムーズに実行される
  -> GitHub にアップロード
  -> ゼアバーに配備
  -> HTTPSドメイン名を取得
  -> 価格設定/規約/プライバシー/返金ページを準備する
  -> パドルに戻ってウェブサイトの検証とチェックアウト設定を行います
```

> 💡 **なぜこれを行うのですか#  **
> Paddle は通常、実際の支払いページを作成する前に、Web サイトが存在するかどうか、開くことができるかどうか、利用規約とプライバシー ポリシーがあるかどうかを確認します。ドメイン名をまだ公開していない場合は、店舗の住所なしでレジに申し込むのと同じように、多くの設定が中途半端になってしまいます。

![支払いシーケンスへの展開](../../assets/diagrams/07-domain-before-paddle.svg)

### ステップ 1: まず、所有しているプロジェクトがこのマシン上で実行できることを確認します。

**【このステップの核心】まず、プロジェクトがコンピュータにインストールおよびビルドできることを確認し、Zeabur にデプロイします。 **

次に、具体的な実行手順を示します。

1. プロジェクトフォルダーを開きます。
2. プロジェクトのルート ディレクトリでターミナルを開きます。
3. 以下を実行します。```bash
npm install
npm run build
```

4. `npm run build` が成功した場合は、次のステップに進みます。
5. 失敗した場合は、完全なエラーを Codex に投稿します。

```text
npm run build に失敗しました。これはエラー ログです。
[完全なログを投稿]

Zeabur にデプロイできるように修正してください。
修復後、再度 npm run build を実行してください。
```

> 💡 **なぜこれを行うのですか#  **
> Zeabur はデプロイ時にビルドも実行します。ローカルのビルドは失敗しますが、通常はクラウドも失敗します。最初に自分のコンピュータで修正すると、間違いを推測するのにかかる時間を短縮できます。

### ステップ 2: バックエンドがハードコーディングされたポートではないことを確認する

**[このステップの核心] Node バックエンドは、Zeabur によって与えられた `PORT` をリッスンし、`0.0.0.0` を使用して外部アクセスを許可する必要があります。 **

Codex にバックエンドの起動コードをチェックさせてください。ターゲットは次のように書きます。```js
const port = Number(process.env.PORT ##  8080);
const serverHost = process.env.PAYMENT_SERVER_HOST ##  "0.0.0.0";

server.listen(port, serverHost, () => {
  console.log(`payment server: http://${serverHost}:${port}/api`);
});
```

このプロンプトを Codex に直接コピーできます。

```text
サーバーの起動コードを確認してください。

要件:
1. ポートは最初に process.env.PORT を読み取る必要があります。
2. ホストはデフォルトで 0.0.0.0 を使用します。
3. localhost をハードコーディングしないでください。
4. ローカル開発に使用できるデフォルトのポート (8080 など) を維持します。
5. 修正後、Zeabur をこのように設定する必要がある理由を説明してください。
```

> 💡 **なぜこれを行うのですか#  **
> 私のパソコンでは、`localhost`は「自分だけに開かれた扉」のようなものです。 Zeaburコンテナでは、自分だけにサービスを公開した場合、外部ユーザーは入ることができません。 `0.0.0.0` は、「このサービスはコンテナの外部からアクセスできる」ことを意味します。

### ステップ 3: プロジェクトに運用開始コマンドがあることを確認する

**【このステップの核心】Zeabur は構築方法と開始方法を知る必要があります。 **

`package.json` を開いて、少なくとも次のことを確認します。```json
{
  "scripts": {
    "build": "npm run build:runtime-careers && tsc --noEmit && node scripts/vite-build.mjs",
    "start": "node server/payment-server.mjs"
  }
}
```

プロジェクトごとに `build` の内容は異なる場合がありますが、原則は同じです。

1. `npm run build` は、フロントエンド静的ファイルの生成を担当します。
2. `npm run start` はオンライン サービスの立ち上げを担当します。
3. オンライン サービスは、フロントエンド ページと `/api/*` の両方を提供する必要があります。

コーデックスに関するヒント:

```text
package.json が Zeabur のデプロイに適しているかどうかを確認してください。

要件:
1. npm run build は実稼働ファイルを生成できます。
2. npm run start は、単一のノード サービスを開始できます。
3. このノード サービスは、フロントエンド dist と /api/* の両方を提供する必要があります。
4. スクリプトが不足している場合は、直接入力してください。
```

> 💡 **なぜこれを行うのですか#  **
> Zeabur はコンピュータの「プレビュー ボタン」をクリックしません。コマンドでのみ実行されます。 Build は「Web サイトをパッケージ化する」ことを意味し、Start は「パッケージ化された Web サイトを他の人がアクセスできるようにエクスポートする」ことを意味します。

### ステップ 4: GitHub リポジトリが最新バージョンであることを確認する

**【このステップの核心】Zeabur に入る前に、デプロイしたい最新のコードがすでに GitHub で利用可能であることを確認してください。 **

次に、具体的な実行手順を示します。

1. GitHub リポジトリ ページを開きます。
2. READMEが正常に表示されることを確認します。
3. 最新のコミットがプッシュしたバージョンであることを確認します。
4. ローカルターミナルで次のコマンドを実行します。```bash
git status
```

5. 未送信の変更がある場合は、前の章の `git add`、`git commit`、および `git push` のプロセスに戻ります。
6. GitHub ファイルリストに `.env` と `.env.payment.local` が表示されないことを確認します。

もう一度、次のファイルを送信しないことを確認します。

-`.env`
-`.env.payment.local`
-`node_modules`
-`dist`
- ログファイル
- 実際の注文情報
-パドルAPIキー
- Webhook シークレット

> 💡 **なぜこれを行うのですか#  **
> Zeabur は GitHub からコードをプルします。コンピュータ上の変更がまだプッシュされていない場合、Zeabur は変更を確認できません。 Zeabur は、ほとんどの場合、GitHub ページに表示されているものをすべて取得します。

### ステップ 5: Zeabur で新しいサービスを作成する

**【このステップの核心】Zeabur を GitHub リポジトリに接続し、コードを Web サイトにデプロイします。 **

次に、具体的な実行手順を示します。

1. Zeabur を開きます。
2. 新しいプロジェクトを作成します。
3. 「GitHub からデプロイ」を選択します。
4. Zeabur が GitHub の認証を必要とする場合は、ページのプロンプトに従って認証を行います。
5. 倉庫リストで、前の章でアップロードした倉庫を選択します。
6. ブランチ (通常は `main`) を選択します。
7. 地域はシンガポールまたは香港に近い地域が優先されます。
8. Zeabur に Node プロジェクトを自動的に検出させます。
9. コマンドの入力を求められた場合は、次のように入力します。

```text
ビルドコマンド: npm run build
開始コマンド: npm run start
```

![Zeabur サービス導入手順](../../assets/diagrams/01-zeabur-deploy.svg)

> 💡 **なぜこれを行うのですか#  **
> リージョンはサーバーが配置されているリージョンです。ユーザーが主にアジアにいる場合、シンガポールまたは香港に近い地域を選択すると、通常、アクセス パスが短くなります。ここでは本土サーバーは必要ないため、ICP 申請は最初のステップではありません。

### ステップ 6: 最初に最小限の環境変数を入力します

**[このステップの核心] 導入の最初のラウンドは、Web サイトを実行するだけであり、Paddle ライブ キーをすぐに入力する必要はありません。 **

まず、Zeabur の変数を入力します。```bash
PAYMENT_SERVER_HOST=0.0.0.0
PAYMENT_STORE_FILE=/data/payment-store.json
PUBLIC_BASE_URL=https://你的-zeabur-域名
CORS_ORIGIN=https://你的-zeabur-域名
PADDLE_ENVIRONMENT=sandbox
PADDLE_ALLOW_UNSIGNED_WEBHOOKS=false
```Zeabur ドメイン名をまだ持っていない場合は、まずそれをデプロイし、ドメイン名を取得してから戻ってきます。```bash
PUBLIC_BASE_URL=
CORS_ORIGIN=
```

実際の URL に変更します。

![Zeabur環境変数表示](../../assets/diagrams/02-zeabur-variables.svg)

> 💡 **なぜこれを行うのですか#  **
> 環境変数は「展開プラットフォームが保持する小さなメモ」のようなものです。コードはこれらの値を読み取ることができますが、フロントエンドのパブリック ファイルにはパッケージ化されません。今後は、Paddle API キーを Web ページのコードに書き込むのではなく、ここに配置する必要があります。

### ステップ 7: `/data` をマウントする

**【このステップの核心】再起動によって失われない保存場所をバックエンドに与えます。 **

次に、具体的な実行手順を示します。

1. Zeabur サービスでボリュームまたはストレージ設定を見つけます。
2. 新しいボリュームを追加します。
3. マウント パスを入力します。

```text
/データ
```

4. 環境変数に次のものが含まれていることを確認します。```bash
PAYMENT_STORE_FILE=/data/payment-store.json
```

![ゼアブルボリュームシグナル](../../assets/diagrams/03-zeabur-volume.svg)

> 💡 **なぜこれを行うのですか#  **
> オーダーおよびロック解除レコードがサービスの一時ディレクトリにのみ存在する場合、サービスの再起動後にそれらのレコードが消える可能性があります。 `/data` ボリュームは、継続的に保存できる小さなハードディスクをサービスに接続するようなものです。

### ステップ 8: オンライン URL を開いて 3 つのページを確認します。

**【このステップの核心】 Web サイト、API、パブリック設定に外部からアクセスできることを確認します。 **

デプロイが成功すると、次のような結果が得られます。

```text
https://your-project.zeabur.app
```

一つずつ開いてください:

```text
https://あなたのドメイン/
https://あなたのドメイン/api/health
https://yourdomain/monetization.json
```

次のことを確認する必要があります。

1. ホームページを開くことができます。
2. `/api/health` はサービスのステータスを返します。
3. `/api/health` はシークレットを表示しません。
4. `/monetization.json` にアクセスできます。
5. `/monetization.json` には、Paddle API キーまたは Webhook シークレットが含まれていません。
6. 模擬支払いプロセスは引き続きテストできます。

> 💡 **なぜこれを行うのですか#  **
> Paddle は後で外部から Web サイトにアクセスします。自分でローカル Web ページを開くことができるだけでは十分ではありません。パブリック URL に実際にアクセスできることを確認する必要があります。

### ステップ 9: Paddle に必要なパブリック ページを準備する

**【このステップの核心】まず、Paddle に入った後に入力する URL がないことを避けるために、支払いプラットフォームが読み取る基本的な指示ページを準備します。 **

パドルは次のことを要求する場合があります。

```text
/価格設定
/用語
/プライバシー
/返金
```

これらのページは最初は非常に単純ですが、少なくとも次のことを記載する必要があります。

1. 何を売っていますか?
2. 支払い後にユーザーが得られるもの。
3. 価格はいくらですか?
4. 1 回限りの購入かどうか。
5. 返金ルールについて教えてください。
6. 問題が発生した場合、ユーザーはどこに連絡すればよいですか?
コーデックスに関するヒント:

```text
Paddle レビューに必要な公開ページの追加にご協力ください。

1. /価格設定
2./用語
3./プライバシー
4./返金

要件:
- 明確かつ控えめに書き、効果を狙って誇張しないでください。
- 雇用、収入、または治療結果を約束するものではありません。
- すべてのページには、Zeabur ドメイン名を介して直接アクセスできます。
- API キー、注文情報、個人の連絡先情報をページに含めないでください。
```

> 💡 **なぜこれを行うのですか#  **
> 決済プラットフォームは、販売しているものが明確かどうか、ユーザーが何を購入したかを知っているかどうか、紛争が生じた場合のルールがあるかどうかを判断する必要があります。ページは簡潔にすることもできますが、空白または曖昧にすることはできません。

### ステップ 10: このドメイン名を Paddle に任せます

**[このステップの核心] 次の章のパドル設定の基礎として Zeabur ドメイン名を使用します。 **

この章を完了したら、次の 3 つの値を記録します。

```text
ウェブサイトのホームページ: https://ドメイン名/
Webhook URL: https://yourdomain/api/webhooks/paddle
ヘルスチェック: https://yourdomain/api/health
```

次の章では、Paddle でそれらを埋めていきます。

> 💡 **なぜこれを行うのですか#  **
> このステップは、店舗を開く前に家番号を取得するようなものです。番地が決定したら、レジ係、支払い通知、およびユーザー バウンス ページに移動する場所ができます。

### この章の完了基準

**[この章の核心] Web サイトがオンラインであることを証明できる必要があります。このマシンでのみ実行できるということではありません。 **

完了後、項目ごとに確認してください。

1. GitHub リポジトリには最新のコードが含まれています。
2. Zeabur が正常に展開されました。
3. ホームページを開くことができます。
4. `/api/health` を開くことができます。
5. `/monetization.json` にはシークレットが含まれていません。
6. `/data`ボリュームが搭載されています。
7. HTTPS ドメイン名を取得しました。
8. Webhook URL は次のようにする必要があることはすでにわかっています。

```text
https://yourdomain/api/webhooks/paddle
```

次の章の Paddle に戻り、このドメイン名を使用して Web サイトの検証、デフォルトの支払いリンク、Webhook、チェックアウトを完了します。
