# 07. 本番稼働チェックリスト

![チェックリストのチャプターアートの起動](../../assets/chapters/chapter-07-launch.webp)
**【この章の核心】 オンラインにする前に、製品プロセス、GitHub、Zeabur、Paddle、環境変数、支払いのセキュリティを 1 つずつ確認してください。 **

オンラインにアクセスする前に、「ページが美しいかどうか」だけを見てはいけません。有料 Web サイトで最も重要なことは、ユーザーが支払いを完了し、支払い後に商品を入手できること、そして支払いをしていない人がそれを回避できないことです。

このリストを 1 つずつ確認してください。

> 💡 **なぜこれを行うのですか#  **
> 有料ウェブサイトのリスクはページの見た目だけではありません。注文、Webhook、キー、ロック解除のいずれかの権限に誤りがあると、ユーザーは「支払ったのに見れない」または「支払っていないのに閲覧できない」という問題に遭遇する可能性があります。

## 1. 基本機能

**[このセクションの核心] まず、ユーザーがホームページからレポート ページに移動できることを確認します。 **

- [ ] ホームページを開くことができます。
- [ ] ユーザーはクイズを開始できます。
- [ ] ユーザーはすべての質問に回答できます。
- [ ] 回答後、`reportId` を生成します。
- [ ] 無料の入門版レポートを表示できます。
- [ ] 支払いがない場合は完全なレポートがロックされます。
- [ ] 支払いボタンは支払いセッションを作成できます。
- [ ] 支払いが完了すると自動的にロックが解除されます。
- [ ] ページを更新した後でも、ロックが解除されたレポートを開くことができます。
- [ ] ブラウザを変更した場合、またはトークンなしでは、他の人の完全なレポートを見ることができません。

## 2.コーデックス納品検査

**【このセクションの核心】Codex に基本的なチェックを実行させ、エラーなしでオンラインにします。 **

Codex を実行します。```bash
npm run typecheck
npm run build
```

失敗しても、無理せずオンラインに接続してください。エラーをコーデックスにポストバックしてください。

```text
これは npm run build のバグです。修正を手伝ってください。
【投稿ミス】
```

## 3. 公開ファイルの検査

**【このセクションの核心】 ユーザーが閲覧できるファイルにシークレットが存在しないことを確認します。 **

ユーザーはこれらのファイルを閲覧できます。

```text
パブリック/*
dist/*
フロントエンドのパッケージ化されたjs/css
```

次のものが含まれていないことを確認してください。

- パドル API キー。
- Webhook の秘密。
- 管理者トークン。
- `.env.payment.local` コンテンツ。
- あなたのプライベートテスト注文情報。

Codex に以下のチェックを依頼できます。

```text
public、dist、およびフロントエンドのソース コードをスキャンして、API キー、Webhook シークレット、および管理トークンが漏洩していないことを確認してください。
```

## 4. GitHub のチェック

**【このセクションの核心】Zeabur が GitHub で最新のセキュリティ バージョンを取得することを確認します。 **

Zeabur は GitHub からコードを取得するため、デプロイする前にリポジトリのステータスを確認します。

- [ ] GitHub リポジトリが作成されました。
- [ ] このマシンの最新の修正がコミットされました。
- [ ] このマシンの最新の修正がプッシュされました。
- [ ] 最新の README とコードは GitHub ページでご覧いただけます。
- [ ] .env がアップロードされていません。
- [ ] .env.payment.local はアップロードされません。
- [ ] Paddle API キー、Webhook シークレット、および管理トークンがウェアハウスに表示されません。
- [ ] GitHub ウェアハウスのアドレスを Zeabur にコピーして使用できます。

##5.ゼアバーの検査

**【このセクションの核心】オンラインサービスが開始でき、アクセスでき、支払い情報が保存できることを確認します。 **

最初にこれを実行して、公的にアクセス可能な HTTPS ドメイン名を取得します。 Paddle の Web サイト検証、デフォルトの支払いリンク、Webhook にはすべてこのドメイン名が必要です。

- [ ] GitHub リポジトリは最新のコードです。
- [ ] Zeabur は正しいリポジトリとブランチを接続します。
- [ ] ビルド コマンドは `npm run build` です。
- [ ] 開始コマンドは `npm run start` です。
- [ ] サービスリスニング `process.env.PORT`。
- [ ] ホストは `0.0.0.0` を使用します。
- [ ] `/api/health` にアクセスできます。
- [ ] `/monetization.json` にアクセスできます。
- [ ] `/data` ボリュームセット。
- [ ] `PAYMENT_STORE_FILE=/data/payment-store.json`。
- [ ] Zeabur HTTPS ドメイン名 (`https://你的项目.zeabur.app` など) を取得しました。

##6. パドルの検査

**【このセクションの核心】Paddle アカウント、ドメイン名、製品、価格、Webhook がすべて準備されていることを確認します。 **

Zeabur の Web サイトを開くことができたら、Paddle を実行します。ドメイン名を持っていない場合は、支払いを強制しないでください。

- [ ] パドルのオンボーディングが完了しました。
- [ ] Web サイトのドメイン名が確認されました。
- [ ] 価格ページは、Zeabur ドメイン名の下にある公開ページに入力します。
- [ ] 利用規約 / プライバシー ポリシー / 返金ポリシーはすべてパス付きの URL を使用します。
- [ ] デフォルトの支払いリンクは検証済みのドメイン名に設定されています。
- [ ] 製品が作成されました。
- [ ] 1 回限りの価格が設定されています。
- [ ] CNY 価格 ID が Zeabur 環境変数に入力されます。
- [ ] USD 価格 ID が Zeabur 環境変数に入力されます。
- [ ] API キーは正しい環境です: サンドボックスまたはライブ。
- [ ] Webhook 宛先は `https://你的域名/api/webhooks/paddle` を指します。
- [ ] Webhook シークレットは Zeabur 変数に入力されます。
- [ ] `transaction.completed` イベントが選択されました。
- [ ] サンドボックス支払いで Webhook をトリガーできる。

## 7. 環境変数のチェック

**【このセクションの核心】展開プラットフォーム上の変数が完全であり、環境が一貫していることを確認します。 **

少なくともZeabur変数。初めてドメイン名を取得したい場合は、Paddle 関連の変数を空白のままにするか、プレースホルダー値を使用できます。 Paddle が製品、価格、Webhook を構築するまで待ってから、それらを入力します。```bash
PAYMENT_SERVER_HOST=0.0.0.0
PAYMENT_STORE_FILE=/data/payment-store.json
PUBLIC_BASE_URL=https://你的域名
CORS_ORIGIN=https://你的域名
PADDLE_ENVIRONMENT=sandbox
PADDLE_API_KEY=...
PADDLE_CNY_PRICE_ID=pri_...
PADDLE_USD_PRICE_ID=pri_...
PADDLE_WEBHOOK_SECRET=...
PADDLE_ALLOW_UNSIGNED_WEBHOOKS=false
```

ライブに移行する場合は、すべてのサンドボックスをライブに置き換えます。混ぜないでください。

## 8. 有料保安検査

**【このセクションの核心】実際の支払いが成功した場合にのみロックが解除されることを確認します。 **

少なくとも次のシナリオをテストしてください。

- [ ] URL と `# paid=true` ではロックが解除されません。
- [ ] セッション ID をランダムに変更してもロックは解除されません。
- [ ] エラー Webhook シークレットのロックは解除されません。
- [ ] 重複した Webhook は複数回発行されません。
- [ ] `transaction.payment_failed` はロックを解除できません。
- [ ] `transaction.completed` のロックが解除されます。
- [ ] 同じ注文に対して別のレポート ID のロックを解除することはできません。

## 9. 実際のユーザーエクスペリエンスのチェック

**【このセクションの核心】 携帯電話とコンピュータを使用して、完全なプロセスを 1 回実行してください。 **

携帯電話で 1 回、コンピュータで 1 回実行します。

- [ ] ホームページのコピーは理解できます。
- [ ] スタートボタンは一目瞭然です。
- [ ] 解答ページをスライドし続ける必要はありません。
- [ ] プロフェッショナルな雰囲気の無料レポート。
- [ ] 支払いボタンがクリアされます。
- [ ] 支払い後に待機中のプロンプトが表示されます。
- [ ] ロックを解除した後、完全なレポートのレイアウトが安定しました。
- [ ] レポートの保存が失敗したり、クリップされたりすることはありません。

## 10. オンラインになる前にテストの入り口を閉じてください

**【このセクションの核心】正式リリース前にテスト用のショートカットをすべて閉じてください。 **

これらのテスト機能がある場合は、公開する前に必ずオフにしてください。

- [ ] ボタンをクリックすると、結果ページに直接ジャンプします。
- [ ] 0元のテストロック解除ボタン。
- [ ] 模擬支払いボタン。
- [ ] 管理コンフィギュレータ エントリ。
- [ ] 任意のデバッグ パネル。

意図的に保管したい場合は、少なくとも通常のユーザーの目につかない場所に保管してください。

## 11. オンライン接続後の初日に見るべきもの

**【このセクションの核心】 リリース初日は、支払いリンクとロック解除の失敗に焦点を当てます。 **

オンラインになった後の訪問数だけを見てはいけません。ハイライト:

- 何人がクイズを始めましたか。
- 何人がクイズを完了しましたか。
- クリックして支払いをした人の数。
- パドルチェックアウトはオンになっていますか?
- Webhook の成功率。
- 支払いが成功した後にロック解除に失敗することはありますか?
- ユーザーから「支払ったのに見られない」という報告はありましたか?
低価格商品で最も恐れられるのは支払いリンクのエラーです。初日のログをもっと読んでください。

## 一文で承認

**【このセクションの核心】 未知のユーザーは、テストを完了し、支払いを行い、完全なレポートが自動的に表示される場合にのみ、オンラインで成功したとみなされます。 **

安定して実行できる場合:

```text
未知のユーザーが Web サイトを開く -> クイズに回答する -> 支払いを行う -> 完全なレポートが自動的に表示される
```

それが本当のオンラインのときです。
