# 02. Codex を使って 0 から Web サイトを構築する方法

![Codex ビルド ワークフローの章アート](../../assets/chapters/chapter-02-codex.webp)
**[この章の核心] Web サイト構築タスクを複数の小さなラウンドに分割し、Codex に各ラウンドで許容できる作業を行うよう依頼します。 **

この章では、**Web サイトの作成方法がわからない場合に Codex をコマンドで実行する方法についてのみ説明します。 **

「完全な商用 Web サイトの構築を手伝ってください」とだけ言って始めないでください。この範囲は大きすぎるため、コーデックスは一度に変更されすぎてしまう可能性があります。 Web サイトを、受け入れ可能な一連の小さなタスクに分割する必要があります。

> 💡 **なぜこれを行うのですか#  **
> 小規模なタスクを処理する場合、Codex はより安定しています。一度に「建物全体を建ててください」と言うのではなく、まず基礎を確認して壁を作り、水道や電気を引くという工事をパートナーに依頼するのと同じと考えると良いでしょう。

## まず、作りたい製品を Codex に伝えます

**【このセクションの核心】まず、Codex に製品の目標と制限を理解させるために、完全なプロンプト ワードを使用します。 **

この段落を最初のプロンプトとしてコピーします。

```text
有料クイズサイトを作ります。

対象となるユーザーは次のとおりです。
1.ホームページを開く
2. 一連のテスト質問を完了する
3. レポートの無料入門版を参照してください。
4. 支払いボタンをクリックします
5. 支払いが成功すると、完全なレポートが自動的にロック解除されます。

最初に使用可能な最小限のバージョンを作成するのを手伝ってください。
要件:
- React + Vite を使用したフロントエンド
- Node.jsを使用したバックエンド
- 最初に模擬支払いを使用し、実際の Paddle は受け入れないでください
- ログインアカウントは必要ありません
- フロントエンドにシークレットを入れないでください
- 各ステップでローカルで実行および検証する方法を教えてください
```

すでにプロジェクトがある場合は、これを追加します。

```text
最初に既存のプロジェクト構造を読み、プロジェクトを再構築しないでください。既存のコーディング スタイルに固執するようにしてください。
```

## 初めてビルドするときは、ビルドするものは小さい必要があります。

**[このセクションの核心] 最初のバージョンでは、プロセスを実行できる最小の Web サイトのみが構築されます。 **

最初のバージョンでは、次のページのみが必要です。

|ページ |目的 |最小要件 |
| --- | --- | --- |
|ホームページ |ユーザーがクイズを開始できるようにする |タイトル、スタートボタン |
|回答ページ |回答を集める |少なくとも 3 ～ 5 つのテスト質問、後で拡張 |
|無料の結果ページ |信頼を築く |部分的な分析を表示しますが、完全なキャリアの回答は表示しません |
|ペイウォール |ロックを解除するブートストラップ |支払いボタン 1 つ、待機状態 1 つ |
|完全なレポートページ |認証ロック解除 |模擬支払い後に完全なコンテンツを表示 |

まだ求めないでください:

- 多言語対応。
- 美しいアニメーション。
-バックエンド管理。
- PDF/長尺画像の保存。
- 本物のパドル。
- 完全な質問バンク。

これらはすべて後で追加できます。最初のステップは、プロセスがスムーズに実行される限り続きます。

> 💡 **なぜこれを行うのですか#  **
> 最小バージョンは最終製品ではありませんが、ルートが実現可能であることを証明するために使用されます。ルートが実現可能になったら、ビジュアル、多言語、レポート保存、実際の支払いを追加することで、より安定します。

## 推奨されるプロジェクト構造

**【このセクションの核心】フロントエンド、バックエンド、データ、構成を分離するには、Codex を事前に必要とします。 **

次の構造に従って Codex を構築するように依頼できます。

```text
有料クイズサイト/
  ソース/
    アプリ/
      App.tsx
    コンポーネント/
    データ/
      質問.ts
    マネタイズ/
      config.ts
    スタイル/
      グローバル.css
  サーバー/
    支払いサーバー.mjs
  公共/
    収益化.json
  パッケージ.json
  .env.payment.example
```

各ディレクトリの意味は次のとおりです。

|目次 |目的 |
| --- | --- |
| `src/app` |ページの流れ |
| `src/components` |ボタン、カード、質問、レポート モジュール |
| `src/data` |質問、結果の種類、レポートのサンプル資料 |
| `src/monetization` |フロントエンドはパブリックな有料設定を読み取ります。
| `server` |バックエンド API、支払いセッション、Webhook |
| `public` |ブラウザに公開できるファイル |

初心者が犯す最も一般的な間違いは、すべてを 1 つのファイルに詰め込むことです。 Codex をディレクトリごとに分割すると、後で保守しやすくなります。

> 💡 **なぜこれを行うのですか#  **
> プロジェクトの構造は保管庫のようなものです。タイトル、ページ、スタイル、支払いインターフェイスはそれぞれ独自の場所に配置されるため、後で特定の部分を変更する必要があるときに、大きなファイルを探し回る必要はありません。

## ラウンド 1: クイズ プロセスのみ

**[このセクションの核心] まず、ユーザーがホームページから結果ページまでの質問に回答できることを確認します。 **

コーデックス宛:

```text
まずメインのテストプロセスを完了し、支払いを受け入れないでください。

要件:
・ホームページに「スタートクイズ」あり
- 回答ページには一度に 1 つの質問が表示されます
- ユーザーは回答を選択した後、次の質問に進むことができます
- 回答後にreportIdを生成します
- 結果ページに移動
- 結果ページには無料の紹介文と「レポート全体のロックを解除」ボタンが表示されます

以下も提供してください。
- npm スクリプト
- ローカル操作モード
- 最小限のテスト方法
```

受け入れ:```bash
npm install
npm run dev
```

ローカル Web サイトを開いて、自分で答えてください。ビジョンを変えることを急がず、まずその道が完成できるかどうかを確認してください。

## ラウンド 2: バックエンドに支払いステータスを保存させる

**【このセクションの核心】 支払いステータスをフロントエンドに独自に決定させるのではなく、バックエンドに任せて保存します。 **

コーデックス宛:

```text
ここで、Node バックエンドを追加し、最初に模擬支払いを行ってください。

バックエンド API:
- POST /api/payments/checkout
  reportId を受信し、支払いセッションを作成し、sessionId と checkoutUrl を返します。

- /api/payments/sessions/:id を取得します
  返品保留中 / 支払い済み / 失敗

- POST /api/payments/mock-complete
  ローカルテストの場合のみ、セッションを有料としてマークします

データは最初に JSON ファイルに保存できます。
フロントエンドがレポートのロックを解除するために URL パラメーターのみに依存できないことを確認してください。
```

受け入れ:

- 支払いが行われていない場合、レポートの全文を閲覧することはできません。
- モック完了後にロックを解除できます。
- ページを更新した後も、バックエンドはレポートがロック解除されているかどうかを認識しています。

## ラウンド 3: ペイウォール スイッチを追加する

**【このセクションの核心】 パブリック設定を使用してペイウォール スイッチを制御し、開発と起動前テストを容易にします。 **

コーデックス宛:

```text
ペイウォールをオンまたはオフにできるようにするには、public/monetization.json を追加してください。

デフォルト:
{
  "有効": false、
  "チェックアウトモード": "API",
  "apiBaseUrl": "/api",
  "プロバイダー": "モック"
}

要件:
- Enabled=false の場合、開発とテストに便利で、完全なレポートを直接表示できます。
- Enabled=true の場合、ロックを解除する前に支払いを行う必要があります
- 公開ファイルには API キーやシークレットを含めることはできません
```

本番稼働前に何度もテストすることになるため、このステップは重要です。スイッチがなければ、簡単に中途半端なペイウォールをユーザーに押し付けることができます。

## ラウンド 4: まず GitHub にアップロードする準備をします

**【このセクションの核心】アップロードする前に、Codex にウェアハウスのセキュリティと `.gitignore` をチェックさせます。 **

ローカルのモック プロセスが完了したら、まずプロジェクトを GitHub へのアップロードに適した状態に整理します。

コーデックス宛:

```text
このプロジェクトが GitHub へのアップロードに適しているかどうかを確認してください。

要件:
- .gitignore は、.env、.env.*、*.local、node_modules、dist、ログ、および一時ファイルを無視する必要があります
- プロジェクトをスキャンして、Paddle API キー、Webhook シークレット、または管理者トークンがないことを確認します。
- README によって他の人がプロジェクトの目的を理解できることを確認します
- 初めて GitHub にアップロードするときに実行する git コマンドを教えてください
- シークレットが見つかった場合は、ファイル パスをリストし、対応するキーを取り消すか置き換えるよう通知してください。
```

承認中は、GitHub リポジトリ内のプロジェクト ファイルを表示できるはずですが、`.env`、`.env.payment.local`、または API キーは表示されません。

## ラウンド 5: 再び Zeabur 導入の準備をする

**【このセクションの核心】Codex がプロジェクトを Zeabur が構築して開始できる形式に整理します。 **

GitHub リポジトリの準備ができたら、まだ急いで Paddle を手に入れないでください。 Paddle は後で Web サイトのドメイン名を入力して確認するよう求めます。また、デフォルトの支払いリンクで開くことができる HTTPS ドメイン名を使用することも要求します。

したがって、正しい順序は次のとおりです。

```text
ローカルモックを実行 -> GitHub にアップロード -> Zeabur にデプロイ -> HTTPS ドメイン名を取得 -> Paddle をセットアップ
```

コーデックス宛:

```text
このプロジェクトを Zeabur に展開できる構造にまとめてください。

要件:
- npm run build はフロントエンド dist を生成できます
- npm run start は同じ Node サービスを開始できます
- Node サービスは dist 静的ファイルと /api/* の両方を提供する必要があります
- サーバーは process.env.PORT をリッスンする必要があります
- ホストは 0.0.0.0 を使用します
- 秘密を漏らすことなく /api/health を追加しました
- .env、.local、node_modules、dist、およびローカル データ ファイルを GitHub に送信しないでください
- ここでは検証可能な HTTPS ドメイン名を取得するだけなので、まだパドル キーは要求しないでください。

次も教えてください:
1. どのファイルを GitHub に送信する必要がありますか?
2.Zeaburのビルドコマンドと起動コマンド
3. Zeabur ではどの変数を最初に設定する必要がありますか?
4. Web サイトと /api/health の両方にアクセスできることを確認する方法
```

この手順が完了すると、次のような公式 URL が作成されるはずです。

```text
https://your-project.zeabur.app
```

この URL には、Paddle の Web サイト検証、価格設定ページ、デフォルトの支払いリンク、および Webhook URL が入力されます。

## ラウンド 6: HTTPS ドメイン名を取得したら、mock を Paddle に置き換えます

**[このセクションの核心] Zeabur ドメイン名を取得した後、Codex を実際の Paddle に接続させます。 **

Zeabur Web サイトが開き、`/api/health` が正常になるまで待ってから、Codex を指定します。

```text
新しい Paddle プロバイダーを追加しますが、モック プロバイダーはそのままにしておいてください。

要件:
- Paddle トランザクション作成 API を使用して POST /api/payments/checkout
- ユーザーの地域またはボタンの選択に基づいて CNY 価格 / USD 価格を使用します
-custom_dataにはreportIdとpayment_session_idが含まれている必要があります
- POST /api/webhooks/paddle を追加しました
- Webhook はパドル署名を検証する必要があります
- トランザクションのみを受け入れます。ロック解除が完了しました
- 繰り返し送信する場合、Webhook は冪等である必要があります
- 間違った署名、一貫性のない金額、一貫性のない価格 ID ではロックを解除できません
```Codex を実装した後、これらのフィールドがどこに設定されているかを示すようにする必要があります。

```text
パドル_環境
PADDLE_API_KEY
PADDLE_CNY_PRICE_ID
PADDLE_USD_PRICE_ID
PADDLE_WEBHOOK_SECRET
PUBLIC_BASE_URL
```

注: `PUBLIC_BASE_URL` には、Zeabur から指定された HTTPS ドメイン名を入力する必要があります。例:

```text
https://your-project.zeabur.app
```Paddle Webhook URL は次のとおりです。

```text
https://your-project.zeabur.app/api/webhooks/paddle
```

## ラウンド 7: 公開前に Codex にセキュリティ チェックを行わせる

**【このセクションの核心】公開前に、Codex に支払い、キー、Webhook、展開リスクをチェックさせます。 **

コーデックス宛:

```text
このプロジェクトが起動に適しているかどうかを確認してください。

チェックすべき重要なポイント:
1. 公開ファイルに API キー、Webhook シークレット、管理トークンはありますか?
2. 支払いのロック解除はバックエンドでのみ確認できるかどうか
3. Webhook は検証されていますか?
4. Webhook を繰り返すと、権限が繰り返し付与されますか?
5. ゼアバーはポートを読むでしょうか?
6. /api/healthを提供するかどうか
7. ビルドおよび開始スクリプトは利用可能ですか?
問題をリストアップし、直接修正してください。
```

## Codex にエラーをどのように報告すべきか

**[このセクションの核心] エラーを報告するときは、アクション、現象、予想される結果、およびログを提供する必要があります。 **

「壊れた」とだけ言わないでください。投稿する内容は次の 4 つです。

```text
私がやったこと：
どのようなエラーが表示されますか:
私はこうあるべきだと予想しています:
関連する画面の説明またはログ:
```

例：

```text
Zeabur で Web サイトを開くと 502 が表示されます。
Zeabur ログには、npm run start が開始されたことが示されていますが、Web ページを開けません。
サーバーが process.env.PORT をリッスンしているかどうか、およびホストが 0.0.0.0 であるかどうかを確認してください。
```Codex は特定のエラーの処理に最適です。具体的であればあるほど速くなります。

> 💡 **なぜこれを行うのですか#  **
> 「Broken」には位置情報がありません。ログ、画面のステータス、実行した内容は、問題の場所を特定するための Codex の手がかりとなります。

## 初心者は検証をスキップしないでください

**【このセクションの核心】 変更が行われるたびに、typecheck と build を実行します。 **

各段階の後に、Codex を実行します。```bash
npm run typecheck
npm run build
```

これらのスクリプトが利用できない場合は、Codex に入力させます。

```text
このプロジェクトにタイプチェックおよびビルド スクリプトを追加し、ローカルで実行できることを確認してください。
```

## この章の完了基準

**【このセクションの核心】この章を完了すると、ローカルで実行可能な模擬有料 Web サイトが作成されるはずです。 **

この章を完了すると、次のことができるようになります。

・ローカルで運営できるクイズサイト。
- ノードのバックエンド。
- 模擬支払いロック解除プロセス。
- 公開プロフィール。
- コーデックスのプロンプトワードの明確なセット。

次の章では、まずプロジェクトを GitHub にアップロードします。 GitHub ウェアハウスの準備ができたら、それを Zeabur にデプロイして HTTPS ドメイン名を取得します。
