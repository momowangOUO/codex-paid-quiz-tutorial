Chapter 01

01. 製品のプロセスを分解する方法

[この章の核心] コードを記述する前に、まず「ユーザーに表示されるページ、各ステップの動作、およびバックエンドが必要なステップ」を明確に分類します。

コードを書き始める前に、次の 1 つの質問に答えるだけで済みます。

ユーザーはサイトにアクセスしてから、ロックを解除するための支払いまでどのような画面を通過することになりますか#

この章ではアーキテクチャ図については説明しませんが、まず製品を Codex が理解できる小さなタスクに分割します。

💡 なぜこれを行うのですか#
Codex には明確なタスク境界が必要です。製品プロセスはロードマップのようなものです。まず、ユーザーがどこに来て、どこで質問に答え、どこで支払いをし、どこでレポートを読んでいるかを把握します。そうすることで、後でコードを書くときに、あちこちで補うことがなくなります。

最初に最短のユーザー パスを描画します

[このセクションの核心] まず、ユーザーがホームページから完全なレポートに至るまでの最短ルートを記述します。

有料クイズ サイトへの最短パスは次のとおりです。

ホームページ
  → 解答ページ
  → 無料紹介レポート
  -> 支払いページ
  -> レポート全文
  -> レポートを保存するか、再度開きます

まだログインする必要はありません。低価格のワンタイムレポートで最も重要なことは、摩擦を減らすことです。

💡 なぜこれを行うのですか#
ログイン、メンバーシップ、バックエンド、割引コードはすべて後から追加できます。最初のバージョンでは、棚をさらに飾る前に、カウンターが実際にお金を集めることができるかどうかを確認するのと同じように、ユーザーは最初に完全な購入を完了できます。

各ページで行うべきこと

[このセクションの核心] 最初のバージョンが重くなりすぎるのを避けるために、各ページは 1 つの主要なタスクのみを担当します。

ホーム

ホームページは、ユーザーを開始させることのみを担当します。

必要なもの:

  • このクイズがユーザーの解決に役立つ問題を説明する 1 文。
  • スタートボタン。
  • オプション: 言語の切り替え、ケースの入力。

最初に「お金を払ってロックを解除する」または「今すぐ購入する」と書かないでください。ユーザーはまだ時間を投資していないため、お金を引き出すのが早すぎると完了率が低下します。

回答ページ

回答ページは、ユーザーが質問に回答できるようにすることのみを担当します。

必要なもの:

  • 現在の質問番号。
  • 質問。
  • オプション。
  • 前の質問/次の質問。
  • 進行状況のプロンプト。
  • 写真または視覚補助。

初心者は、最初に 5 問のテスト バージョンを実行し、プロセスが完了したら 48 問に拡張することをお勧めします。

無料導入レポート

無料版は刺激を目的としたものではなく、また空虚な話でもありません。ユーザーにあなたがプロフェッショナルであると思わせます。

表示できるもの:

  • 中心的な心理的要因。
  • 行動傾向と潜在的な行き詰まりポイント。
  • 自己認識と外部パフォーマンスとの間のギャップ。
  • 完全なレポートではどのような方向に分析が続けられるか。

表示しない:

  • キャリアに関する完全な回答。
  • フルパス。
  • 詳細な行動計画。
  • 保存可能な完全なレポート。

ペイウォール

ペイウォールではユーザーは支払いのみを許可されます。

必要なもの:

  • 現在の価格。
  • 明確な支払いボタン。
  • 支払い後に指示が自動的にロック解除されます。
  • 支払いが失敗または保留中のステータス。

一度に多くの支払い方法ボタンを詰め込まないでください。バックエンドは、地域に基づいて入り口を推奨できます。

完全なレポート

完全なレポートは、ユーザーに「これは単なるランダムなテキストではない」と感じてもらえるはずです。

以下を含めることができます:

  • キャリアレーダー。
  • 心理学的プロファイリング。
  • 適切なキャリアタイプ。
  • 複数の開発ルート。
  • リスク境界。
  • 別の方向。
  • レポートを保存します。

[このセクションの核心] ページ、ユーザー アクション、バックエンド参加方法を表に整理し、Codex に送信します。

製品プロセスを次の表に整理し、Codex に投稿します。

ページユーザーに表示されるものユーザーができることバックエンドが関与する必要があるか

レポート ID とは何ですか?

【このセクションの核心】 reportId は、特定のテストレポートの番号です。

reportId はレポートの番号です。

ユーザーが質問に回答すると、フロントエンドまたはバックエンドは reportId を生成し、その後のすべてのアクションはそれを中心に展開します。

この回答 -> reportId
この注文 -> レポート ID
今回のロック解除 -> reportId
この完全なレポート -> レポート ID

reportId がないと、支払いプラットフォームは「誰かが支払いました」と通知し、どのレポートのロックを解除すればよいのかわかりません。

💡 なぜこれを行うのですか#

>reportIdはピックアップ番号のようなものです。ユーザーが食事を注文し、支払いをし、食事を取りに戻ってくるとき、同じコンテンツに対応するには同じ番号を使用する必要があります。

支払いセッションとは何ですか?

[このセクションの核心] payment_session は、特定の支払い試行の記録です。

payment_session は支払いの試行です。

ユーザーは次のようなことを行う可能性があります。

  • クリックして支払いますが、ページを閉じます。
  • 支払いに失敗しました。
  • 支払いを再試行します。
  • 支払いは成功しましたが、フロントエンドがジャンプバックしませんでした。

したがって、フロントエンドの状態だけに依存しないでください。保存するバックエンド:```json

{

"sessionId": "pay_xxx",

"reportId": "rep_xxx",

"provider": "paddle",

"providerOrderId": "txn_xxx",

"status": "pending"

}


支払いが成功したら、次のように変更します。```json
{
  "status": "paid",
  "paidAt": "2026-05-28T00:00:00.000Z"
}
💡 なぜこれを行うのですか#
レポートには複数回の支払い試行が含まれる場合があります。ユーザーは初めて支払いページを閉じる可能性がありますが、2 回目は成功します。 payment_session は、ステータスの混乱を避けるために、これらの試行を個別に記録できます。

アクセストークンとは何ですか?

【このセクションの核心】 accessToken は、支払いが成功した後に完全なレポートを開くためのキーです。

accessToken はレポートを完了するための鍵です。

支払いが成功すると、バックエンドは推測不可能なトークンをレポートに送信します。次回ユーザーが戻ってきたときに、フロントエンドはトークンを使用してバックエンドに質問します。

このトークンにはレポート reportId を表示する権限がありますか#

完全なレポートは、バックエンドが「はい」と応答した後にのみ表示されます。

💡 なぜこれを行うのですか#
完全なレポートを表示するには、「誰かがこのレポート ID に料金を支払った」ということだけに頼るべきではありません。そうしないと、他の人が同じレポート ID を表示できる可能性があります。 accessTokenは専用の鍵のようなもので、鍵を持っている人だけが開けることができます。

最初のバージョンでは何もできません

【このセクションの核心】 最初のバージョンでは、ロックを解除するために 1 回限りの支払いが必要であり、複雑な機能を実行しないと起動が遅くなります。

より速くオンラインにするには、最初のバージョンをスキップできます。

  • ユーザー登録。
  • バックエンド CMS。
  • 割引コード。
  • 購読する。
  • 複雑なデータベース。
  • 自動メール。
  • 複数の製品パッケージ。

ロックを解除するには、まず 1 回限りの支払いを行ってから、ゆっくりと追加料金を支払う必要があります。

💡 なぜこれを行うのですか#
製品の初期段階で最も確認する必要があるのは、「テストを完了して料金を支払う意思のある人がいるかどうか」です。最初に多くの周辺機能を実行するよりも、最初にこの主要な行を実行する方が価値があります。

## ラウンド 2: バックエンドに支払いステータスを保存させる

**【このセクションの核心】 支払いステータスをフロントエンドに独自に決定させるのではなく、バックエンドに任せて保存します。 **

コーデックス宛:

ここで、Node バックエンドを追加し、最初に模擬支払いを行ってください。

バックエンド API:

  • POST /api/payments/checkout

reportId を受信し、支払いセッションを作成し、sessionId と checkoutUrl を返します。

  • /api/payments/sessions/:id を取得します

返品保留中 / 支払い済み / 失敗

  • POST /api/payments/mock-complete

ローカルテストの場合のみ、セッションを有料としてマークします

データは最初に JSON ファイルに保存できます。

フロントエンドがレポートのロックを解除するために URL パラメーターのみに依存できないことを確認してください。


受け入れ:

- 支払いが行われていない場合、レポートの全文を閲覧することはできません。
- モック完了後にロックを解除できます。
- ページを更新した後も、バックエンドはレポートがロック解除されているかどうかを認識しています。

## ラウンド 3: ペイウォール スイッチを追加する

**【このセクションの核心】 パブリック設定を使用してペイウォール スイッチを制御し、開発と起動前テストを容易にします。 **

コーデックス宛:

ペイウォールをオンまたはオフにできるようにするには、public/monetization.json を追加してください。

デフォルト:

{

"有効": false、

"チェックアウトモード": "API",

"apiBaseUrl": "/api",

"プロバイダー": "モック"

}

要件:

  • Enabled=false の場合、開発とテストに便利で、完全なレポートを直接表示できます。
  • Enabled=true の場合、ロックを解除する前に支払いを行う必要があります
  • 公開ファイルには API キーやシークレットを含めることはできません

本番稼働前に何度もテストすることになるため、このステップは重要です。スイッチがなければ、簡単に中途半端なペイウォールをユーザーに押し付けることができます。

ステップ 1: まず、リンク全体で Paddle が何を行うかを理解します。

【このステップの核心】Paddle は集金と支払い結果の通知を担当し、Web サイトは注文の作成とレポートのロック解除を担当します。

ユーザーがクリックしてロックを解除する
  -> ウェブサイトのバックエンドが支払いセッションを作成します
  -> バックエンドが Paddle にチェックアウトの作成をリクエストします。
  -> ユーザーは Paddle ページで支払います
  -> Paddle は Webhook を使用してバックエンドに通知します
  -> バックエンドは支払いが有効であることを確認します
  -> バックエンドのロック解除に対応するレポート ID
  1. チェックアウトを作成します。
  2. Webhook を受信して​​確認します。
  3. 支払い確認後にアクセス権が発行されます。

💡 なぜこれを行うのですか#

custom_data は、Paddle の注文に記入した「付箋」です。 Webhook が戻ってくると、バックエンドはこのメモに基づいて、この支払いがどのレポートと支払いセッションに対応しているかを認識します。

ステップ 10: Webhook のみでレポートのロックを解除できるようにする

【このステップの核心】 ユーザーがページに戻った、URL にさらに多くのパラメーターがある、またはフロントエンド表示が成功したからといって、直接ロックを解除しないでください。

Paddle はバックエンドに次のように通知します。

POST /api/webhooks/paddle

バックエンドは次のチェックを行う必要があります。

  1. Paddle-Signature を生のボディで検証します。
  2. transaction.completed のみ受け付けます。
  3. custom_data.payment_session_id を確認します。
  4. custom_data.report_id を確認します。
  5. 価格 ID を確認します。
  6. 金額を確認します。
  7. 通貨を確認します。
  8. 繰り返される Webhook は冪等である必要があります。
  9. すべてのチェックに合格した後にのみ、accessToken を書き込みます。

コーデックスに関するヒント:

POST /api/webhooks/paddle を実装してください。

要件:
1. パドル署名を検証するには生の本文を使用する必要があります。
2.transaction.completed ロック解除のみが受け入れられます。
3.transaction.payment_failed/transaction.canceled/transaction.past_due はロックが解除されていません。
4.custom_data の reportId とpayment_session_id はローカル セッションと一致する必要があります。
5. 価格ID、金額、通貨が一致しない場合、ロックを解除できません。
6. 繰り返し Webhook 権限を繰り返し発行することはできません。
7. トラブルシューティングを容易にするために、エラーはすべてpayment_events に書き込まれる必要があります。
💡 なぜこれを行うのですか#
ユーザーの支払いページが Web サイトに戻ります。これはブラウザが戻ったことを意味するだけで、入金が確認されたことを意味するものではありません。本当に信頼できる信号は、Paddle サーバーから送信される署名検証済みの Webhook です。
